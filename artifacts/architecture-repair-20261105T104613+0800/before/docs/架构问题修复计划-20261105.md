## 1. 目标和取舍

保留发行版原生用户态、同发行版共享实例、CID/UUID/generation 校验、原生包事务与恢复机制。按故障边界修复控制层，不做无关的大规模重构。

| 问题 | 根因 | 本次目标 | 优先级 |
|---|---|---|---|
| F01 多环境包操作回归 | 服务要求独立只读清单，真实 runtime 未实现，fake 提前支持 | 真实能力闭环，支持范围明确；不再用 fake 成功替代产品能力 | P1 |
| F02 合法事务互判隔离失败 | 每环境写锁与全管理根前后观察范围不一致 | 同管理根受管包写入明确排队，完整覆盖观察窗口；未知外部变化仍拒绝 | P1 |
| F03 后台应用提前释放租约 | 启动器返回被当成实际应用结束 | 租约绑定可验证执行所有权，未知状态可恢复，避免误停共享实例 | 条件性 P1 |
| F04 bundled 候选不保证加载 | 按名称消缺，没有验证对象实际搜索路径 | 静态候选、加载验证、工作流验收分开报告和判定 | P2 |

第一版 F02 选择串行化，不立即引入允许跨环境包写入并发的复杂协议。代价是同一管理根包操作吞吐下降；应用运行不因此全局串行化。未来若需要并行，再设计操作代际、可归因变更及一致快照，不能只忽略“有另一个事务”的变化。

## 4. S1 / F02：管理根级包操作协调

修改重点：`service.py` 的包事务、恢复、隔离观察入口；如需抽离，新增小型协调模块及针对性测试。先枚举所有改变包清单或环境集合的正式入口，不能只包住 install。

设计要求：

- 引入按管理根身份确定的跨进程协调锁，覆盖 before 观察、目标写入、清单提交、after 观察和最终事务持久化。不能只用 Python 线程锁。
- install、update、remove、install-local、repair-dependencies、pkg recover 使用一致协调规则；会改变同伴集合的 create/remove/登记变更也必须协调或以集合代际拒绝不稳定样本。
- 现有每环境包锁与原生数据库锁保留。新增锁以“协调锁 → 环境包锁”为拟定顺序；实施前审查 lease/start/stop/recover 的完整锁图。任何持有环境锁后回取协调锁、内部 stop 重入或 lease 环路必须先消除，不照搬顺序硬套。
- 排队有期限、取消和明确状态；等待期间不得启动容器或写原生包数据库。持锁者崩溃由 OS 释放文件锁，持久事务仍走恢复流程，不能靠删除锁文件解锁。
- root 级锁只协调本产品入口，不能阻止外部 Podman/原生包管理器变更。不可归因变化、数据库忙、观察不一致仍为失败或 UNKNOWN；不自动吸收为新基线。

验收用例：

| ID | 必须证明的行为 |
|---|---|
| FIX02-01 | 两个 fake 环境并发提交，第二个在第一轮观察窗口结束后执行，两者 completed |
| FIX02-02 | 两个独立宿主测试进程共享同一协调锁，原生模拟写入不会交叠 |
| FIX02-03 | 同环境原有串行行为保留；排队超时/取消不产生原生写入 |
| FIX02-04 | 持锁者异常退出后可进入恢复；不丢事务，不卡死，不跳过 needs-recovery |
| FIX02-05 | 模拟外部同伴变更仍被检出；环境集合改变不被漏检 |
| FIX02-06 | install/repair/recover 与 lease/start/stop 组合没有锁反转；用有界 barrier/事件验证，禁止无限等待 |

本阶段并发均为受预算保护的离线小进程/fake 环境；不运行两个真实容器。通过只说明协调机制成立，不说明 F01 已恢复。

## 5. S2 / F01：真实只读包清单能力

修改重点：`runtime.py`、`service.py`、必要的新只读数据库适配模块；相关 runtime/包操作/CLI 测试。禁止把整个容器文件系统导出或加载到内存来完成一次查询。

### 5.1 先定义能力，再实现适配

将当前隐式 `getattr(read_inventory_readonly)` 提升为明确契约。结果至少包含：支持状态及原因、完整 CID/环境代际、目标发行版与数据库类型、读取方式、规范化清单摘要、观察时间/一致性证据。接口签名可在实现评审时确定；fake 和真实 runtime 必须遵守同一语义。

- 能力探测不能 start/restart/exec 同伴，也不能改变其挂载、配额或登记；查询前后重新核验实例绑定。
- 已登记清单不是实时读取结果。缓存只能作为比较基线，不能填充缺失观测。
- 采用有界只读数据库文件读取或经验证的快照适配。首先 T0 确认当前 Podman/rootless 存储接口与权限能否满足；不预设 mount/cp 等接口天然安全或可用。
- 数据库读取应限制文件集合、字节数、期限，防路径逃逸及链接跟随越界；资源/临时对象必须可归属。需要挂载或其他副作用的方案先明确分类，不能称纯只读查询而跳过准入。
- Debian、Arch、RPM 数据库分别定义规范化清单。与既有 `_read_inventory_record()` 的包名、版本、架构、状态、排序、编码语义对齐；不比较两种不同序列化结果的哈希。
- 停止态数据库先完成真实支持。运行态同伴若无法获得一致视图，应明确拒绝，不能使用“读两次相同”冒充原子快照。数据库锁、日志/WAL、半写入和外部写者需有处理规则。
- RPM 后端、版本或宿主工具不匹配时明确 unsupported；不安装宿主依赖或解析猜测值来凑完整矩阵。

### 5.2 首版范围与退出条件

按 Debian → Arch → RPM 能力评估推进。每个适配器分别交付，不因 Debian 通过宣布所有发行版通过。若某后端无法在现有限制下独立读取，保留前置拒绝并标记 F01 PARTIAL/BLOCKED，列出缺失能力与后续方案；不改成无证据放行。

| ID | 必须证明的行为 |
|---|---|
| FIX01-01 | 原 CLI 命名空间回归通过；无同伴、一个同伴、多个同伴分别覆盖 |
| FIX01-02 | 同一合法数据库 fixture 的只读输出与既有原生查询规范化结果一致；覆盖版本/架构/状态边界 |
| FIX01-03 | 能力缺失、损坏/忙数据库、超预算、实例替换、读取中代际变化时，在 native 写入前拒绝 |
| FIX01-04 | fake 声明能力与真实适配契约一致；实际 PodmanRuntime 支持性另有断言，不靠给 fake 添方法消除失败 |
| FIX01-05 | 同管理根真实同伴分支：目标操作完成，同伴无 create/start/restart/exec，独立清单前后相符 |

FIX01-05 需要合规的既有同管理根多环境 fixture。当前审查记录中的固定池不满足该分支，不能迁移登记、另起管理根或新增容器补齐。若执行时仍无适用 fixture，该项 BLOCKED；离线通过不替代真实验收。

## 6. S3 / F03：统一实际执行所有权与 APP 租约

修改重点：`on_demand.py`、`runtime.py`、`exec_control.py`、`project_sessions.py` 以及 APP 启动调用链。优先复用已有身份握手/probe/cancel 机制，避免复制第三套控制协议；不能假定记录一个 PID 或 PGID 就能追踪所有双重 fork/setsid 子进程。

定义三种执行语义：

1. 前台命令：被管理执行及其已登记后代全部结束后才释放租约。
2. 后台应用：绑定客体内可持续监督的执行组/应用生命周期；启动器退出后仍持有租约。选择能处理 daemonize/setsid 的客体 supervisor 或可验证分组，先证明覆盖；无法建立所有权时明确拒绝自动生命周期模式或保持 UNKNOWN。
3. 单实例激活：本次短启动请求结束不等于既有应用结束。只有可验证的应用协议/实例映射才转移或关联租约；无法确认时不猜测。

执行记录至少关联完整 CID、环境代际、执行 token、客体 PID/starttime、监督者身份及状态。状态需区分 starting、running、exited、unknown、recovery-required；身份变化或 probe 失败不当作 exited。

主控/APP worker 退出后，旧租约清扫必须先检查实际客体所有权，不能因宿主 PID 消失直接删除租约、撤掉 bridge 或停止容器。最后租约释放须同时满足执行结束、无其他租约、仍有本轮 auto-stop 所有权。用户自行启动/重启的环境继续保留。

旧状态迁移采用版本化兼容读取；缺客体身份的旧活跃 lease 不补造身份、不直接清扫。保留可恢复状态与明确处置入口。取消只作用于精确核验的本次执行，禁止按进程名杀应用。

验收：前台正常退出；启动器返回而子进程仍活；双重 fork/setsid；单实例激活；两个应用先后退出；APP 与项目会话共存；worker 崩溃与重连；PID 复用/CID 替换；probe 超时；用户手动预启动环境；旧 lease 读取和恢复。先 T1 模拟，后固定 CID 内微型进程，再私有显示 GUI。

完成条件：后台存活时 lease/bridge 保留，最后实际执行结束后按所有权收尾；失败状态可恢复，不误停共享应用。WPS 影响仍需真实“打开→编辑→保存→关闭→重开”证明，模拟反例修复不等于 WPS 验收。

## 7. S4 / F04：静态依赖与实际加载分层

修改重点：`dependencies.py`、结果输出/CLI 展示和相关测试。保留已有 `runtime_loading=unverified` 的含义及原生包事务结果。

- 将“缺失已解决”“发现 bundled 候选但可加载性未知”“已验证加载失败/通过”明确区分。不要把候选直接呈现为全部依赖可用；保持旧 JSON 兼容并增加证据范围，若必须变更状态枚举则同时升级消费者与文档。
- 对每个 ELF 对象记录依赖边、RPATH/RUNPATH、ORIGIN、架构等；明确 RUNPATH 传递性、加载环境、插件入口及符号版本等未覆盖范围。静态解析不声称完整模拟动态加载器。
- 先实现可信微型 fixture 的有界加载验证，使用目标发行版加载器、普通用户、私有环境和受控入口。不能对任意不可信程序直接执行宿主 ldd，不在宿主运行客体程序，不修改全局 LD_LIBRARY_PATH。
- 无法安全验证的对象保持 unverified。一次 main 加载成功不能证明 dlopen 插件、外部命令、桌面服务或全工作流成功。

验收矩阵：原“库存在但不在搜索路径”反例；有效 ORIGIN/RUNPATH；同名错误架构；符号版本不满足；传递依赖；插件运行时 dlopen；无/多 provider；索引失败；provider 安装后仍不能加载。静态判断与实际加载结果须分别断言，不只检查 completed。

完成条件：原反例不会被展示为运行可用；有效/无效加载路径结果有实际证据；未支持项明确保留。真实自动补库仍走正式入口和天然缺库 fixture，不卸载公共库造故障。
