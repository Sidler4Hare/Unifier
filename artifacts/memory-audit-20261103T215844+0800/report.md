# 内存与性能瓶颈审计（2026-11-03）

## 判断

**DeepSeek 将内存列为重要原因有实证支持；把整次桌面崩溃直接定性为 OOM 杀进程或唯一内存根因，证据不足。** 本轮补充了早先“根因 UNKNOWN”汇总没有展开的证据：10:29:04 内核真的发生过高阶物理页分配失败，同期宿主内存阻塞明显。此前没有 OOM kill 回执，不能被解释成“没有内存问题”。

这是只读诊断：没有启动客体或应用、没有改资源/交换/桌面设置，没有改项目实现；只新增本报告和采样回执。分析对象为旧 boot 在北京时间 10:00–10:42 的故障链。先前停止的测试数据、容器和日常部署保留。

## 故障时间线与因果范围

| 时间 | 直接观察 | 能支持的结论 |
| --- | --- | --- |
| 10:14–10:19 | KWin 多次报告主线程暂时挂起。 | 桌面已有卡顿；这几条日志本身未指明内存原因。 |
| 10:19:15 起 | Debian 客体含飞书/WPS：cgroup 无内存、CPU 限额，557 个任务、32 个进程；宿主大量使用 swap。 | 应用并发和资源治理不足，详见后表。 |
| 10:22:25 | KWin `atomic commit failed: 权限不够`。 | DRM/显示提交失败已发生，早于下面的 Wi-Fi 分配失败；不能用后者直接解释这条错误。 |
| 10:28:53–10:29:02 | 进入 S3 休眠并唤醒。 | 故障处在设备恢复场景。 |
| **10:29:04.350** | `kworker/5:0: page allocation failure: order:4`；调用栈 `dma_direct_alloc → iwl_pcie_txq_alloc → iwl_mvm_add_new_dqa_stream_wk`；随后 `iwlwifi: Tx queue alloc failed`。 | **Intel Wi-Fi 发送队列申请连续物理内存失败，内存问题已是实际失败，不只是占用偏高。** |
| **10:29:10** | 宿主 PSI memory `some avg10=21.40`、`full avg10=18.93`。 | 同期存在明显的全局内存阻塞，不只是累计 swap 数字高。 |
| 10:36:55 | dsh 启动元数据含 `loginctl terminate-session 2`。 | 恢复操作发起了会话终止；该记录不是 OOM killer 记录，也不单凭启动元数据推断所有后续执行结果。 |
| 10:37:29 | 多个 Wayland 客户端几乎同时断连、随后 ABRT。 | 客户端随显示会话丢失退出；不能把每个 ABRT 各算一次 OOM。 |

[内核原始节选](kernel-allocation-excerpt.json)、[KWin 时间线](kwin-timeline.json)、[压力峰值及时间](host-pressure-peaks.json)、[恢复动作](recovery-actions.json)、[完整检索范围](incident-journal-summary.json) 可复查。该窗口读取 176 条内核记录，找到 1 次 page allocation failure，未找到实际内核 OOM kill 或 `systemd-oomd` 进程记录。内核休眠时的 `OOM killer disabled/enabled` 不是杀进程证据。保留日志可能不覆盖未写出的失败，阴性检索不作绝对证明。同一旧 boot 在本轮之前也有 KWin atomic commit 错误，见 [先前日志](prior-kwin-errors.json)。

本机页大小为 4096 字节，order 4 对应 16 页、**64 KiB 连续物理内存**。[内核分配 API](https://docs.kernel.org/core-api/mm-api.html) 说明高阶分配的连续页要求。故障转储中 Normal 区普通的 32/64/128/256/512/1024 KiB 空闲块都是 0，仅有一个标为 H 的 2 MiB 高原子预留块；Normal free 209964 KiB、报告的 min 206416 KiB，低于 low 222292 KiB。这支持“容量余量很低且高阶空闲块枯竭/碎片化”的判断，不能简单说总内存每个字节都用完。

同一转储各 zone 的 zspages 合计 **2,791,060 KiB，约 2.66 GiB 物理内存**；总逻辑 swap 使用约 9.65 GiB。zspages 是转储中的 zsmalloc 区域统计，不是当时完整 `zram/mm_stat` 快照；结合本机 zram swap 配置，它强烈提示压缩交换的物理 RAM 成本很高，但不能把其每字节都精确归给某个应用。[ZRAM 统计说明](https://www.kernel.org/doc/html/v7.2/admin-guide/blockdev/zram.html) 区分逻辑数据、压缩数据与实际分配 RAM。ZRAM 会消耗物理内存和压缩/解压 CPU，不是额外增加了等量 RAM。

`full avg10=18.93` 是 10 秒趋势中所有非空闲任务同时受内存资源阻塞的时间占比指标；不是“用掉了 18.93% RAM”，也不是整段 18 分钟都停顿了 19%。定义见 [内核 PSI 文档](https://docs.kernel.org/accounting/psi.html)。

**较有依据的综合解释**是：高应用负载与大量换页压缩了物理余量，碎片化使唤醒后的设备分配失败；与此同时显示栈已有故障，后续恢复操作又终止了会话。内存是应优先治理的重要因素；Wi-Fi 分配失败是否直接导致桌面退出、最初 DRM 权限错误为何出现，仍未证明。

## 项目实际占用与主要来源

下表使用不同计量口径，**不得纵向相加**。PSS 是分摊后的驻留页；SwapPss 是逻辑换出页，不能当作额外物理 RAM；cgroup 包含文件缓存和内核计费，也与 PSS 重叠。

| 层级/负载 | 已测数字 | 解释与边界 |
| --- | --- | --- |
| **飞书** | 10:19:15 的 21 个进程合计 **444.60 MiB 驻留 PSS + 1423.46 MiB SwapPss**；10:37:21 仍有 14 个进程、1256.06 MiB SwapPss。 | 此次最大的已归属应用负载。仅看最后低 RSS/PSS，会漏掉大量换出状态。后台保留并不自动等于内存泄漏；退出/保留策略与实际收尾需要修复和验证。 |
| **WPS 同期进程** | 首样本含 2 个 wps、2 个 wpsoffice、4 个 CEF helper 和 cloudsvr；驻留 PSS 约 58.5 MiB，另有约 219 MiB SwapPss。 | 已被大量换出，低驻留不能解释成低工作集。共享入口、CEF、云后台会扩大多组件开销。 |
| **整个 Debian 客体** | 65 个样本；当前值 129.8–788.3 MiB；观测到的 cgroup 历史峰值 **2156.6 MiB**；逻辑 swap 1245.0–1729.8 MiB。 | 峰值发生的精确时刻未知，不能把峰值与另一次 swap 峰值相加当同时占用。第一帧 557 个任务包括线程，进程实际是 32 个。 |
| Arch 纯 CLI/SQLite 客体 | 同期当前内存 **8.3–12.4 MiB**，5 个任务、基本不换页。 | 同一台机器上的轻量对照观察；并非完整 GUI/包管理负载。基础容器不是默认就耗数 GiB 的完整虚拟机。 |
| 后续单应用私有显示客体 | Sheet 聚合模式峰值 674.9 MiB；独立模式 654.7 MiB；Slides 602.2 MiB；Compare 78.4 MiB。 | 含 Xvfb、库、缓存与内核内存，不是应用独占 PSS，也不是原生/容器 A/B。不能从这两次 Sheet 快照承诺独立模式固定节省多少 RAM。 |
| 包管理峰值 | 10/21 的小包安装实验：APT **177.1 MiB**、DNF **414.9 MiB**、pacman **298.1 MiB**。 | 历史小包结果，只用于证明包任务也会抢预算，不能当作所有更新的上界；原生事务不能与重 GUI 无节制并行。 |

汇总算法和来源见 [历史资源](historical-resources.json)、[单应用回执](workload-footprints.json)。历史 Debian 在约 18 分钟内又发生 1.76 GiB 逻辑换入、2.04 GiB 逻辑换出和 472945 次 major fault；它自己的 CPU 计费增加 83.31 CPU 秒。换页字节不等于实际磁盘传输，ZRAM 也计在其中；major fault 不全是 swap。宿主图形合成、压缩交换等全局成本并不都记在应用 cgroup 内，不能用这组 CPU 均值证明没有卡顿。

另外，不能把所有失败都归为 RAM：Sheet 聚合模式错误那次 `memory.events oom=0/oom_kill=0`，而 `pids.events max=5`；限制的是进程加线程的任务数。后续同一 192 任务上限的独立模式未再命中。直接把测试用的 192 任务阈值推广到所有产品工作负载，也会人为制造应用失败。

## 当前基线和正式产品缺口

21:59:49 的 [只读快照](current-host.json)：可用内存约 **3.51 GiB**，ZRAM 实际分配约 **0.77 GiB**，内存 PSI 近期接近 0；这是当前恢复状态，不能回填为上午状态。

- Codex 应用及其 helper 的 43 个用户进程：驻留 PSS **1.30 GiB**，另有约 **1.61 GiB 逻辑 SwapPss**。这是开发工具成本，不能归为 Unifier 本体；也不能拿此刻数字断言上午工具占用相同。
- 共枚举到 108 个本用户进程，PSS 有 6 个读取失败；桌面与其他应用分组仅报告部分和，不补零。root/其他 UID 进程、GPU 驻留与共享图形缓冲没有完整分摊，保持 UNKNOWN。
- 本轮 dsh 的 Qwen 路由是网络远端服务，[路由核验](model-route.json) 未导出凭据；此路径没有在这台 8GB 电脑加载模型权重。不能把服务端模型权重算成本机内存。本次没重新测服务端进程。
- 所有 10 个本用户容器均停止。测试 slice 此刻任务为 0，残留约几十 MiB 主要是 file/slab 计费；进程退出后的缓存计费本身不是活进程泄漏。大镜像占磁盘，不会自动全部驻留 RAM。

**最优先的产品缺口**：实际 inspect 的原 9 个容器均 `Memory=0`、`NanoCpus=0`，即未设置对应硬上限；任务上限是 Podman 默认的 2048。只有新测试 fixture 有 768 MiB/1 CPU/192 任务上限，见 [实际配置](container-limits.json)。当前源 [creation_argv](../../src/unifier/runtime.py:346) 也没有正式资源策略字段；[guarded_test](../../tools/guarded_test.py:38) 的保护只是测试适配器。已安装入口仍指向 `0.0.2-b656bf73abfe`；最新工作树保护没有部署到日常程序。

所以，机器只有约 7.43 GiB 可用物理总量会放大问题，但“默认不限额 + 无全局准入/并发预算 + 未核实后台退出”是项目需要负责的设计缺口。

## 代码中其余性能与扩展性成本

| 路径 | 源码事实 | 判断 |
| --- | --- | --- |
| GUI 启动/租约 | [on_demand](../../src/unifier/on_demand.py:348) 为托管启动维持工作进程和租约，最终释放依赖真实执行结束；手工预启动的环境会保留。 | 不能把关窗口等同退出，也不能强杀整个发行版破坏其他应用；需要验证单个应用关闭、最后一个应用关闭、后台保留三种状态。 |
| 控制面输出 | [runtime](../../src/unifier/runtime.py:1022) 在 capture 路径使用 `subprocess.run(capture_output=True)`。 | 存在大输出一次性进内存风险；交互执行并非全部捕获。尚无证据证明这条路径造成上午主故障，宜增加有界输出/流式落盘。 |
| JSON 注册表/请求账本 | [json_records](../../src/unifier/json_records.py:42) 整文件解析、逐记录验证，写时再次整表序列化；[agent ledger](../../src/unifier/agent_bridge.py:765) 多次扫描所有记录。 | 长期请求增长会增加内存峰值、锁持有、序列化与 fsync 成本；单帧/单回执限长不等于整个账本有界。这是静态扩展风险，不是已证实的泄漏或上午主因；未知执行记录不能靠清空/TTL 删除来换性能。 |
| FUSE 元数据与页缓存 | [projection](../../src/unifier/projection.py:45) 默认节点/目录条目各 65536、目录字节账面预算 8 MiB；[fuse_view](../../src/unifier/fuse_view.py:174) 每次真实属性重验证会失效普通文件页面。 | Python 对象、排序/集合临时副本与 FD/内核缓存不等于账面字节数；重复失效会增加回源和 CPU。属于索引/多文件压力重点，但此次普通共享 bind 的应用工作流不能算 FUSE 负载。不能删掉一致性保护来制造性能提升。 |
| 受管复制 | [流式复制](../../src/unifier/file_operation_publish.py:80) 按 1 MiB 分块；随后校验暂存与源并 fsync。 | 不是整文件装进 Python 内存。代价是多遍逻辑读取、哈希、写回和页缓存压力；是否实际重复访问磁盘取决于缓存，不能直接宣称 3 倍磁盘读。 |
| 原生包查询与依赖扫描 | 文件列表、ELF 扫描和仓库查询依赖多个原生命令，部分输出捕获。 | 要以包清单/文件身份和仓库索引版本作正确失效键再缓存；当前没有该路径的独立 CPU/RAM 剖面，不虚构优化百分比。 |

当前既没有“同版本应用在宿主原生与容器内”的交错 A/B，也没有单独测到全部 GPU/合成成本。保护测试还限 1 CPU、使用软件渲染，其启动/操作耗时不能当作日常原生性能。现有证据支持瓶颈排序，不支持“兼容层额外损失 X%”或“已经发现 Python 泄漏”的结论。

## 优化次序与验收

1. **P0：把资源治理做进正式运行路径。** 为项目/环境/宿主侧 worker 建统一总预算；启动前按实时可用余量、PSI 与换页压力做准入；包事务和其他后台重任务排队。不同应用的任务数、内存和突发需求分别校准，不能机械照搬测试配额。保留宿主交互余量，OOM/中止后记录真实未知状态并走恢复，不能用成功返回掩盖失败。
2. **P1：治理实际大头及生命周期。** 优先飞书后台、WPS 聚合/CEF/云组件；只在独立测试 profile 中做有条件 A/B。核对托管应用真正退出、共享后台所有权和最后租约收尾；不按进程名字全局 kill，不擅自删除账号/profile 或关闭用户要求常驻的功能。
3. **P1：建立四阶段基线。** 同一合成文档、相同网络/视频条件，重复“停止→空闲→打开/编辑/保存→关闭后稳定”；同时采 cgroup anon/file/kernel/swap、PSS/SwapPss、任务数、CPU、PSI、ZRAM 物理占用。先串行，再按预算并发；不可读指标保留 UNKNOWN。验收同时看数据正确、退出/租约、宿主卡顿与压力，而不只看峰值下降。
4. **P2：再改控制面与数据路径。** 输出有界/流式；账本增量化或索引化并保留持久去重/未决状态；FUSE 对象与失效机制分别测量；最后评估重复哈希/扫描的 CPU 和缓存成本。不要从镜像瘦身、跨发行版混用 `/usr` 或无证据的全局 swap 调参开始。

本次没有执行这些优化，也没有换参数重现崩溃。内存治理必须推进；KWin/休眠恢复链仍需独立处理，不能承诺减内存就能消除已观察到的所有桌面故障。
