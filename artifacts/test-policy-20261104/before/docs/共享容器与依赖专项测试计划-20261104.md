# 共享容器与依赖专项测试计划

日期：2026-11-04（Asia/Shanghai）　版本：1

本轮交付的是新计划，没有执行其中的应用、安装或容器生命周期测试。所有用例初始为 `NOT_RUN`。当前代码和停止态容器只做只读核对；旧扩大测试的通过记录不计入本计划。

## 1. 本轮要回答的问题

1. 多个同发行版应用是否真正复用同一个容器实例，而不是每个应用、安装动作或测试用例各起一套环境？
2. 共享实例内，应用启停、租约、包事务和依赖变更是否会误伤其他应用？
3. 正式安装入口能否自动补齐声明依赖、未声明的 ELF/插件运行库，并在重复操作时复用已有依赖？
4. 超出静态补库能力的命令、加载路径、ABI、桌面服务和厂商故障，能否准确报告边界，避免“补库通过”被当成“应用全部可用”？

这里的“共享容器”指**同一管理根内，同发行版的多个应用绑定并使用同一个完整 CID**。共享一个目录、使用同一镜像或给多个容器起相似名称，均不算通过。共享环境也不提供同一 UID 下敌对应用之间的安全隔离。

## 2. 范围和容器数量

| 项目 | 固定规则 |
|---|---|
| 主线 | Debian 13，共享实例、包事务、依赖和一个轻量 GUI 工作流 |
| 复核 | Arch，主线完成后按预算执行最小子集；同样复用既有 CID |
| 本机测试池 | 最多选择 2 个既有测试 CID，每个发行版最多 1 个；同一时刻最多 1 个测试容器运行 |
| 新增容器预算 | **0**；禁止每用例 `podman run`、复制一个新环境、失败后另建环境绕过问题 |
| 真实多应用并发 | 一个测试作业内最多 3 个轻量应用进程组，共享同一个 CID；不与模型、解包、编译或其他测试作业并行 |
| 包事务并发 | 只允许锁竞争用例提交两个小请求；实际包数据库写入必须串行，不并行维护不同发行版 |
| 暂不扩展 | 本机 Fedora 客体、其他新发行版、会议账号/音视频、跨宿主、Agent 大矩阵、完整 GPU 性能和长压 |

本机宿主为 Fedora，不能为凑齐矩阵创建 Fedora 客体。旧容器不会在本计划中自动删除；本轮选择之外的历史环境和两个日常环境保持原状态。规划时 inspect 到 **10 个容器，运行数 0**，详见[停止态清单](../artifacts/shared-container-dependency-plan-20261104/inventory-readonly.json)。

### 2.1 候选实例与复用门槛

| 角色 | 既有候选完整 CID | 已核对状态 | 使用前仍需核对 |
|---|---|---|---|
| Debian 主实例 | `e58754f0645ae1ff2924cb09a7264cc821e44893e7589a7fd0ebca09ce5f5e45` | 停止；仅挂载自己的测试共享目录；已有私有 GUI 工具 | 原管理根记录、UUID/generation、应用清单、账号配置保护、限额是否足以完成选定小负载 |
| Arch 复核实例 | `d78a392cb1750fc95f5e0476806cfda25b6b06a8c018d2277b01e38bab3fddf8` | 停止；无宿主挂载 | 原管理根记录完整性、原生包数据库、keyring、是否需要超预算的整体升级 |

Debian 候选目前有 768 MiB / 1 CPU / 192 任务的旧测试限额；Arch 候选没有 CPU/RAM 配额、PID 上限为 2048。这些是**现有测试环境状态，不是产品默认策略或本轮性能结论**。本计划不自动修改它们。若选定负载触及限额，记录 `INVALID_RESOURCE_LIMIT` 并停止该负载，不能判为项目性能失败或自动放宽限额。

复用前必须验证原所有权和管理记录。不能只拿一个 CID 直接用 Podman 执行软件、跳过 Unifier 来凑通过率，也不能无记录重建或迁移它的所有权标签。管理记录缺失、身份不符、桌面挂载不安全、已有状态无法恢复时，停止并出具精确阻断原因；**不自动切换其他历史容器**。

## 3. 首个阻断项：观察其他环境不应唤醒它们

本轮只读发现：`src/unifier/service.py` 的 `_other_fingerprints()` 遍历同一管理根内其他环境；`_probe_inventory()` 对停止的环境执行 `start → 读取包清单 → stop`。包事务前后都会用到其他环境指纹。这条路径可能造成“操作一个环境，却看到其他环境反复启停”。

这是**源码已确认的行为，尚未在本轮实机复现**，与“每次新建容器”是两个不同问题。

`PRE02` 必须先通过离线可控运行时复现，再完成修正与回归，实机依赖阶段才可开始：

- 非目标容器在全程不得出现 `create/start/restart/exec` 事件，原停止状态不变。
- 停止环境的隔离校验应使用受支持的只读包数据库视图或可验证快照；若无法独立核验，明确报告未核验/拒绝相关操作，不能将缓存冒充实时证据。
- 不允许通过关闭隔离校验、删掉其他环境登记或更换成没有同伴记录的新管理根，让测试表面通过。
- 离线用例必须覆盖两个同管理根环境；实机若缺少安全、完整的同伴登记，相关真实边界为 `BLOCKED`，不能仅靠“全局其他容器没启动”宣称验证过该代码分支。

## 4. 执行方式与公共准备

### 4.1 代码与入口

- 明确使用当前工作树入口，并记录 HEAD、相关源码 SHA-256、脏文件和控制器版本；不混用旧安装版 Unifier。开始修复代码后需要生成新的执行指纹。
- 所有正向安装、补库、卸载和应用启动走 `unifier install`、`unifier pkg ...`、`unifier app ...` 正式路径。安全适配层可以限制实例/资源和显示访问，不能替代产品的包事务、依赖扫描、租约或验证步骤。
- 私有解包仅可用于构建/检查测试输入，不作为“正常安装并自动补库通过”的证据。禁止手工补库后回填自动补库成功。
- 验收记录最终事务的 `phase`、`failure_phase`、`dependency_repair.status`、`verification.ok`、隔离校验和原生退出码；日志里出现一条安装命令不算成功。

### 4.2 测试材料和干净状态

- 优先使用两个小 CLI 应用 A/B 和一个可控插件 fixture，所有测试文件、包名、SONAME 带本轮唯一前缀。每个 fixture 有源码、构建参数、包内容、架构、哈希、预期输出。
- fixture 在客体所属工具链中构建，构建阶段与运行阶段分开；不把宿主库复制进客体、伪造 SONAME 或通过软链接凑版本。
- 未声明依赖用例需要**事先证明库确实缺失**。从目标可信仓库挑选唯一提供者、未安装且不会破坏基线的微型运行库，并冻结查询结果和 fixture 的 `DT_NEEDED`；不能通过卸载 WPS/其他应用已经需要的公用库制造故障。
- 若没有合适的天然缺失库，先报告 `BLOCKED_FIXTURE`。要使用专用签名 fixture 仓库，需另列准备方案并核验当前仓库适配边界；不冒充发行版官方仓库、不关闭签名检查、不临时扩容器池。
- 无候选/多候选、索引错误、补装无效等危险分支先用现有 fake runtime/受控响应离线测试。缺失条件、可观测证据不完整的实机样本不得记为真实修复成功。
- 顺序复用同一环境：用唯一 fixture 或移除本轮独有测试包恢复条件；只清理确认归属的测试输入。不为获得“干净状态”重建容器或删除公用库。
- 每轮冻结包来源/版本/哈希、索引状态和依赖清单；缓存按内容哈希复用，避免重复下载。仓库、签名或网络失败与解析算法故障分开报告。

### 4.3 GUI 与能力准备

- GUI 仅选择已有安装的 WPS Writer 加一个小 CLI，证明真实应用共用环境；不为本轮再装一批大型应用。若版本/注册不完整，先通过正式入口准备，开销超过预算则延期。
- 使用新建的独立测试 HOME/XDG/TMP/字体缓存/私有显示，不使用已登录飞书或旧 WPS 账号配置。测试目录在允许的私有共享根内，禁止访问宿主活动 X0、Wayland、DBus、音频、GPU、摄像头。
- 显示和控制器先独立自检；不能在正式租约生命周期用例开始前手动启动容器，使自动停止所有权被改变。自动停止契约先用 CLI 验证；GUI 的显示引导必须在首次受管启动后接入，无法做到就把该 GUI 生命周期边界记为未测。
- 外部命令与 GUI 基线检查包括 `gio`、字体/MIME 工具、Qt 后端所需库及所需桌面服务。当前 ELF 补库不负责全部能力；缺失不能被“静态补库成功”掩盖。
- WPS 原生端云辅助崩溃、厂商 GPU JSON 尾逗号、Qt 内部告警分别登记。禁用云服务只能验收本地功能，不能将完整套件标为 PASS；也不能只压掉 stderr。

## 5. 用例矩阵与分阶段执行

共 **32 个用例**：5 个准入/准备、10 个共享容器、13 个依赖、3 个 Arch 复核、1 个收尾。每个用例的步骤、观察点和通过条件见[用例卡](../artifacts/shared-container-dependency-plan-20261104/cases.md)，可机读版见 [plan.json](../artifacts/shared-container-dependency-plan-20261104/plan.json)。

| 阶段 | 用例 | 执行原则 |
|---|---|---|
| 0：只读与离线 | PRE01–PRE05；DEP09/10/12 的负向契约 | 不启动实机环境，先处理 PRE02 阻断项；现有离线测试只运行相关模块 |
| 1：Debian 共享 CLI | SH01–SH08 | 两个轻量应用共用固定 CID，覆盖冷/热启动、关闭一个/最后一个、启动器退出、失败回收、手动启动所有权 |
| 2：Debian 依赖 | DEP01–DEP13；SH09 | 正式入口安装/补库、共享依赖、重复操作、卸载与升级影响、锁竞争和受控恢复；应用 GUI 全部关闭 |
| 3：真实 GUI 共享 | SH10 | 仅 GUI 能力准备通过后执行；Writer + 小 CLI，最多 5 轮、累计最多 10 分钟；正常保存/重开有独立 oracle |
| 4：Arch 最小复核 | AR03 → AR01 → AR02 | Debian 完成且停止后再做；先核对整体升级/签名/预算；不能用部分升级换取执行 |
| 5：统一收尾 | END01 | 无论成功、失败、中止都执行，只作用于本轮选定 CID 和本轮测试对象 |

优先级 P0 为本轮核心验收；P1 为有额外 fixture/资源条件的升级、恢复、GUI 循环和 Arch 复核，不能自动升级成本机长压。涉及下一阶段的必要准备仍须通过，优先级不提供绕过阻断项的理由。

### 5.1 共享容器必须有的证据

- 同管理根、同发行版、同 environment UUID/generation、同完整 CID；多应用不增加容器/环境记录。
- 在一个冷启动共享组里：容器 start 事件恰好 1 次；热启动后续应用新增 start 事件为 0。准备阶段的启动与被测阶段分开计数。
- 关闭一个应用时，另一个应用的 PID/start、租约、心跳和可写文件仍正常，容器不停止；最后一个真实应用结束时，仅由该组自动启动的实例才自动停止。
- 用户/测试明确手动启动的环境不应在最后租约退出时被擅自停止；测试最终自行回到原状态。
- CLI 应用每个实例有独立 token/argv/cwd/env/输出，不串参数；WPS 单实例复用窗口是应用行为，不能强制要求一个窗口对应一个进程来凑并发数。
- CID 替换、外来标签、代际变化、未知客体执行不能通过删租约、杀整个容器或另建实例“恢复成功”。

### 5.2 依赖必须有的证据

- “包声明依赖自动安装”“未声明 ELF/插件依赖补装”“应用实际加载成功”分别记录。
- 两应用共用提供者时，记录同一个包版本、实际加载路径和库文件标识；不能只凭同名库推断 ABI 可用，也不从磁盘 reflink 推断 RAM 共享。
- 重复 repair 不再安装不需要的提供者，不重复造环境；查询、校验、必要的索引访问可以发生，需记录，不虚构“绝对零网络”。
- 卸载 A 后 B 仍能执行相同功能，共用库未被误删。升级用 fixture 的兼容版本，不能直接更新或卸载正在运行的真实 GUI 公用依赖。
- 未声明脚本命令、纯运行时拼接 `dlopen`、ABI 符号不匹配、厂商配置错误、缺桌面服务，要保留清楚的能力边界。当前尚未实现的自动修复列为 GAP，不能以“超范围”为理由把全应用可用性标为 PASS。
- 两个包事务只能串行写原生数据库；中断后先 `pkg recover` 重读清单和状态，未知时拒绝继续改包，不能换容器避开恢复。

## 6. 本机保护与预算

沿用[本机测试规范](本机测试规范.md)，下列规则对本轮显式生效：

- 一个测试作业、一台测试容器；内部最多三个轻量进程组。模型编码、包准备/解包、编译、GUI 运行互相串行；需要修代码时再按既有 dsh 本地 Qwen 单任务方式处理，先停止实机负载。
- 启动前保留至少 2 GiB 宿主余量，加本阶段预估峰值与安全余量；至少 30 秒低压力窗口。没有峰值时先做最小 CLI/单 GUI 样本，拒绝直接叠加大应用。
- 独立保护器每 250 ms 采样；MemAvailable < 2 GiB 连续两次、full PSI avg10 > 3% 或 some > 10% 连续 2 秒时停止本轮；读不到指标、控制器失联或总期限到达也停止。
- 核对 cgroup 祖先和真实负载位置。只限制 Podman 命令或控制器不代表整个容器已受限；产品工作进程、后台重启路径也必须受相同准入和停止锁约束。
- 本轮不更改生产 CPU/RAM 默认策略，不通过降低保留线或自动提高既有限额维持测试。旧 `docs/扩测保护与恢复.md` 的 768 MiB/1 CPU 是特定历史 fixture 配置，不是本轮新增的产品通用要求；如使用旧适配器，其实际硬限制仍必须满足，不能声称已取消。
- 一段实机执行最多 45 分钟；到期停止并记录剩余 NOT_RUN，不自动扩展。CLI 观察通常最多 120 秒；GUI 单用例最多 600 秒；包准备单步骤最多 900 秒，均由独立控制器限时。
- 阶段准备预估额外下载超过 200 MiB，或 Arch 整体升级超过该预算时，暂停该阶段并报告包清单/预计大小，不执行部分升级、不自动转成大规模下载。历史锁定的大安装包优先复用缓存，重新安装也要说明实际写入/解包成本。
- 正式结果记录 memory/PID/OOM 事件和 CPU 节流；测试配额造成的失败单列 INVALID，不能归为产品内存缺陷；本轮不发布吞吐/帧率排名。

保护停止：先冻结本轮动作队列，按 PID/start/CID 身份结束本轮执行和显示，再停止该测试启动的环境。不得为探测状态重新启动未选中的容器；保留中止锁和事务回执后才可进入新的明确尝试。

## 7. 结果、已知缺口与停止条件

### 7.1 每条结果

状态仅用 `NOT_RUN / PASS / FAIL / BLOCKED / INVALID`，另有 `product_scope`、`feature_gaps` 和 `execution_mode`。负向用例在正确拒绝时可 PASS，但不等于相应功能已实现。

最少保存：case ID、源码/fixture 指纹、执行模式（离线/真实）、管理根/UUID/CID、开始/结束状态、原生 argv/退出码、包清单和事务、依赖扫描与候选、实际功能输出、租约快照、容器事件、资源与中止、恢复结果。账号/令牌/Xauthority 原文不进入公开证据。

最终报告按以下范围分开：共享运行时、声明依赖、未声明静态 ELF 补库、实际运行加载、外部命令/桌面能力、原生交互、恢复。不能只给一个模糊的“依赖功能已全通过”。

### 7.2 规划时的明确缺口

| 编号 | 观察 | 当前证据 | 对执行的影响 |
|---|---|---|---|
| G01 | 包清单交叉校验会临时唤醒同管理根内停止的其他环境 | 当前源码 | PRE02 硬阻断，先离线复现修正，再进入实机包事务 |
| G02 | 静态补库不检查脚本外部命令、符号版本和全部实际搜索路径 | 源码与现有功能文档 | DEP08/11/12 必须区分现有契约与待实现能力 |
| G03 | 上轮私有解包和旧 CLI 环境跳过正式安装准备 | 上轮 WPS 对照记录 | 正向依赖验收统一正式入口，禁止手工补齐后冒充自动通过 |
| G04 | 旧测试环境的登记、账号状态、限额和基础依赖可能不适合复用 | inspect 只核对了部分条件 | PRE01/03/04/05 全部满足后方可启动；条件不足即 BLOCKED |
| G05 | 原生云辅助 SIGSEGV、厂商 GPU JSON 格式和其他应用内部警告 | 上轮应用日志和静态检查 | 不计为补库器统一故障；本地功能和完整套件分别验收，不在本轮反复触发崩溃 |

遇到容器新增、非目标被启动、日常数据变化、未核准挂载、产品工作进程绕过保护、无法收尾的事务/租约，立即中止后续实机测试。已通过的定义内用例不反复重跑；修复后只回放失败用例和直接受影响的共享/依赖边界。

### 7.3 收尾

- 新增容器数为 0；选定测试实例回到开始状态，非选定容器状态和数据不变。
- 本轮应用、保护器、虚拟显示、转发监听全部退出；核对 boot/KWin 身份、未遗留可自动重启的任务。
