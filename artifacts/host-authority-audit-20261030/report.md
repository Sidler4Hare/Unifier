# 母发行版权威与同派系容器准入审计

核查日期：2026-10-30，Asia/Shanghai。结论：旧版本确实允许宿主同发行版及同派系容器；当前工作树已有策略版本 2 的拒绝补丁，但尚未形成全入口、部署与交付闭环。本轮只新增本目录的审计材料，没有修改产品实现、暂存内容、部署副本或真实容器。

这里的“同派系”指宿主与客体属于白名单中的同一 family，包括 Ubuntu → Debian；另行核查了同一个客体 target 的多实例入口。Fedora、RHEL、SUSE 仍按当前设计分为三个 family，没有擅自改变派系定义。

## 真实测试回执也证明问题存在

本地保存的三宿主首轮测试记录仍是策略 1。Ubuntu 的 `ubuntu/live-20261030T204909/headless.json` 明确记载 `host.id=ubuntu`、`target=debian13`、`relationship=same-family`、`allowed=true`，且有真实 CID、包查询与重开结果。它证明此前实际创建运行过同派系容器，并非只有静态代码可能性。

其他宿主回执的摘要保存在 `result.json` 的 `server_receipts`。这些是既有远端测试回执，本轮没有 SSH 重查远端当前状态。同派系生命周期通过只能证明旧版容器机制执行成功，不能计入当前设计验收。

本机现场 Fedora 44 的 rootless Podman 只有 Arch FreeCAD 与 Debian 腾讯会议两个停止容器，没有 Fedora 同派系容器。策略 2 当前矩阵为 Debian 允许、Fedora 拒绝、Arch 允许。

## 当前仍存在的缺口

1. **部署与发布不一致。** 终端使用策略 2，但旧桌面部署和两个分发包使用策略 1，暂存区也仍是策略 1。同一产品因入口不同获得不同准入结果。现有两个日常应用属于跨派系，不能据此声称它们当前违规；风险是旧副本与分发包仍保留放行能力。

2. **运行中容器的目录浏览绕过执行检查。** `src/unifier/shortcuts.py:975` 的 `_guest_list_running()` 校验所有权和运行状态后直接调用 `runtime.exec()`，没有调用宿主关系拒绝。完整 `unifier ls debian13 / --json` 的隔离反例中，模拟旧 Debian 容器已运行并将当前宿主切到 Ubuntu：普通 `service.run()` 明确拒绝，`ls` 却返回 0 且到达 `/bin/sh -c`。这不是新建容器绕过，也没有证明任意参数注入；它证明“禁止同派系执行”没有覆盖所有客体执行路径。停止环境的宿主侧只读恢复视图与此不同，可以作为数据恢复入口保留。

3. **每发行版唯一容器只约束快捷层。** `EnvironmentService.create()` 在 `src/unifier/service.py:314` 只拒绝相同 env ID，未拒绝相同 target。交叉派系的模拟宿主上，先后以 `debian-one`、`debian-two` 创建 `debian13`，两个均成功。这不绕过策略 2 的宿主同派系拒绝，但低层 `env create --id` 仍提供通用多实例能力。若“一发行版一个日常容器”也是产品硬约束，需明确诊断/实验入口和正式产品入口的适用边界，并在服务侧落实。

4. **策略变更影响状态语义与测试判断。** `src/unifier/cli.py:605` 的 matrix 只要任何目标拒绝便返回 1。本机 Fedora 在合法排除 Fedora 客体、其余两个允许时仍返回 1；自动化不能再用这个退出码代表“宿主整体不兼容”。旧 enabled/selected 状态和旧回执也不能当成当前 allowed；运行操作虽有主服务拦截，列表最好明确显示“保留但被策略阻止”。

## 隐患及影响边界

同派系克隆会让本可由母发行版管理的软件形成另一份包状态、升级与来源记录，增加应用选择、默认关联、权限撤销和数据归属的歧义；容器系统层、缓存与常驻进程也可能重复消耗资源。本轮没有测量这些额外资源的具体数值。

共享项目是可写 bind，桌面集成还可暴露被授权的显示、音频和设备通道。同派系容器仍可能修改它获准访问的共享文件，必须纳入宿主统一授权与撤销。禁止同派系可减少不必要的第二套执行域，但不能代替这些访问控制。

**没有证据证明“同派系”本身会让容器获取宿主 root 或自动覆盖宿主包数据库。** 当前后端要求 rootless，环境系统树和包数据库保持独立。本次确认的是产品准入错误、入口策略分叉及残留执行旁路，不应写成已验证的提权漏洞。

正确产品边界应保持：宿主同派系由宿主原生域负责；获准跨派系才进入 Unifier 客体；拒绝客体请求时明确报错，不把显式客体命令偷偷转交宿主执行。普通 Docker/Podman 用户自建容器不属于 Unifier 的全局封禁范围。

## 验证与后续修复落点

- 当前离线全量回归：558 项，554 通过、4 条件跳过，日志 `regression.log`。未设置真实集成或证据测试开关。回归通过并未覆盖本轮 `ls` 反例。
- `probe.py` 可重放策略差异、主服务同派系创建拒绝、完整快捷 `ls` 旁路和诊断多实例；使用临时目录、注入宿主事实与 fake runtime。策略副本单独在当前导入环境下求值，不代表完整旧部署运行验收。
- `result.json` 记录源码哈希、策略版本、矩阵、容器清单、回执摘要与上述反例。全程没有拉镜像、安装包或操作真实容器生命周期。

修复应从统一服务侧准入、补齐目录浏览的客体执行检查、明确 target 唯一性边界开始，再同步部署副本、更新分发包和暂存内容。已有违规环境应保留数据与查看/停止/恢复入口，不因升级策略自动删除或自动强停。新规则的实机验收需补“同系拒绝且零创建/执行副作用”和“跨系原功能不退化”，并分别记录源码、部署和远端结果。
