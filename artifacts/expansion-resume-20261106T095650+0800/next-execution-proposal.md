# 后续测试装置调整提案

2026-11-06 用户授权了下面的 384 MiB 档。该档已用于 `inventory-pilot-384/`，容器启动前再次出现 `CONTROLLER_INVALID_RECLAIM_PRESSURE`。同一保护类不再自动复试。下文保留当时的测量和未扩大的边界。

当前控制器保持 192 MiB MemoryMax、144 MiB MemoryHigh、64 TasksMax、0 swap。共享 APP 作业触发宿主 PSI（full avg10 12.68%，some 13.64%）并安全停止；更保守的下一阶段在控制器约 144 MiB、high 事件 156 时提前停止，容器尚未启动。汇总峰值分别约 368/340 MiB，无新增 OOM/max/pids 事件；不能据此判产品性能不合格。

提议只调整下一次 transient 测试控制器：MemoryMax=384 MiB、MemoryHigh=288 MiB、TasksMax=128。监测器仍为独立 64 MiB/16 任务；既有测试 slice 仍是 **总共 1 GiB RAM、128 MiB swap、256 任务、1 CPU**，宿主保留线仍为 1 GiB，30 秒低 PSI 准入、250 ms 监测和全部中止线保持。原客体 768 MiB/192 任务及配置不变；子组预算重叠时由汇总组强制限制总量，不将子组上限之和当可额外使用的资源。不操作宿主全局设置或日常应用。

实施范围为 tools/reuse_test_guard.py 的有界 spec 参数和实际 unit 限额核验、相关离线回归，以及一份新尝试 spec。默认值保持当前值，不能让旧 spec 暗中扩额。增加 memory.stat 采样，分别记录匿名内存/文件缓存和各子组指标。每个阶段单独准入，最多一次有依据复试，同类保护再次触发即结束阶段。

执行顺序：先当前源离线回归；停止态包库读取与引用释放 pilot；若通过，再两应用共享 pilot，最后最多三个轻量应用。均复用原完整 CID、原管理根、UUID/generation。旧中止锁与失败证据保留，禁止清锁或换 runtime 绕过。实机包事务另需材料与包库边界满足，预览下载/写入预算后才准备工具链；当前尚未执行 dependency-probe。

此方案不能解除同管理根第二个合规环境缺失、Arch 无合规配额、私有 GUI 尚未准入等独立阻断，也不授权新建容器、迁移记录或改旧容器配额。上述事项保持 BLOCKED。

依据 docs/测试禁令与规范.md 第 4.2 节：“增大资源/并发/时长必须先给出已有测量、宿主承受能力和具体方案，并得到用户对该变更的明确授权，不自动提高。”因此当前没有修改或运行上述 384 MiB 配额。需用户明确授权此 transient 控制器调整后执行。
