# v0.0.8 过渡大修与 v0.0.9 接入准备

日期：2026-11-16（Asia/Shanghai）。状态：**硬件与缺陷回归继续验收**。各项当前结果见 [当前状态](../docs/当前状态.md)，日用补丁与 v0.0.8 候选分别记录。

本版是硬件接入和现有三目标稳定性的过渡大修。硬件范围为本机核显、服务器两张 NVIDIA V100 与 AMD Radeon HD 7470，以及两端 CPU。纳入日用反馈和项目缺陷的复现、修复与回归验收，为下一版新增客体准备公共接口。用户已批准 Intel/AMD 两个专用测试根及容器和 AMD 单节点临时 ACL 后恢复。[DRM 专项回执](../artifacts/v008-gpu-drm-20261115T183930+0800/report.md)

### 2.1 GPU 能力分工

| 能力 | Iris Xe | V100 | HD 7470 |
|---|---|---|---|
| 设备选择/实际 UID 权限 | 必测 DRM | 必测 NVIDIA/CDI | 必测 DRM，不能要求必须是 amdgpu |
| EGL/OpenGL 离屏图形 | 必测 | 驱动提供时补测，计算主线不依赖桌面 | 必测，优先核对 radeon/r600 路径 |
| Vulkan 图形 | 主测 | 有兼容驱动与预算时补测 | 先做能力判定；不列为必须成功的正向项 |
| GPU 计算 | 优先 Vulkan compute；OpenCL 可用时补测 | CUDA 主测，FP32/FP64 及小型混合精度矩阵 | OpenCL 仅在实际后端支持时补测；不预设 ROCm/HIP |
| 视频解码 | VA-API 主测 | 核对 NVDEC 能力后补测 | H.264 为首个候选，核对 VA-API/VDPAU 实际暴露 |
| 视频编码 | VA-API 主测 | 核对 NVENC 能力后补测 | 不预设专用硬编码器，能力判定与软件回退诊断必做 |
| 多卡/混合厂商选择 | 与宿主实际设备身份对齐 | 单张逐一选取，核对未选 GPU 未执行负载 | 与 V100 共存时明确选中 AMD，不能误用另一张卡 |

HD 7470 按老款 Radeon 路径准备。X.Org 的设备族/驱动表与 Mesa 的 r600、RADV 分工用于建立候选判定，最终由实际 PCI 芯片身份和驱动确认；不能因为名称带“HD 7000”就当作 GCN，不能因 Vulkan 枚举出软件设备就宣布硬件 Vulkan 可用。[Radeon 驱动表](https://www.x.org/RadeonFeature/) · [Mesa 源码分工](https://docs.mesa3d.org/sourcetree.html) · [RADV 支持范围](https://docs.mesa3d.org/drivers/radv.html)

HD 7470 不作为现代 AMD ROCm 的成功样本。ROCm 的型号、版本和系统支持必须单独匹配；缺少支持不以更换宿主驱动或强制架构覆盖绕过。[AMD 系统要求](https://rocm.docs.amd.com/projects/install-on-linux/en/latest/reference/system-requirements.html)

Intel 各编解码格式、位深和 profile 单独登记，不由“Tiger Lake”或存在 VA-API 推断全部支持。固件或低功耗编码条件缺失时报告原因，本版不自动修改 i915 模块参数或固件配置。[Intel media-driver](https://github.com/intel/media-driver)

V100 的计算能力为 7.0；CUDA 13.0 已移除 Volta 的离线编译与库支持。计划优先锁定支持 `sm_70` 的 CUDA 12.x 工具链/运行库组合（12.9 为候选），实际版本以服务器驱动、客体编译器和依赖兼容核验为准。`nvidia-smi` 显示的 CUDA 上限不等于实际工具包或样例可运行。[NVIDIA GPU 表](https://developer.nvidia.com/cuda/gpus/legacy) · [CUDA 13.0 发行说明](https://docs.nvidia.com/cuda/archive/13.0.2/cuda-toolkit-release-notes/)

NVIDIA 官方视频表列有 V100 的编解码能力；计算卡定位不直接推导“无 NVENC/NVDEC”，也不等于该板卡和当前驱动已可用。以准确型号、运行时能力查询及输出验证决定补测项。[NVIDIA 视频支持表](https://developer.nvidia.com/video-encode-decode-support-matrix)

若服务器发行版或实例池变化，按派系准入重排，不能放行同派系客体。首轮每个硬件在一个合规客体上完成适用主测，另一客体只复核公共契约与代表样例；不扩成所有驱动/格式/发行版的全组合。每张参与验收的 V100 至少逐张完成设备身份、权限和小算例；多卡并行不在本版范围。

硬件实机前，先根据 [当前状态](../docs/当前状态.md) 对照 [路线图六项基础门槛](远期规划-2026-11-08.md#2-近期三个现有目标) 和所选实例的 PRE03 证据登记准入。已有轻量 CLI/GUI 的通过不覆盖新增 GPU/驱动进程。所需基础门槛未满足就阻断对应实机阶段；运行态一致快照等已明确拒绝的能力继续按边界处理，不要求借硬件专项扩成新功能。

默认新增容器预算 0；每宿主最多选择两个既有测试 CID，同一时刻最多一个测试容器。本专项初轮两台机器也串行推进。日常 FreeCAD、会议与模型服务不作为可接管的测试对象。

**设备是现有环境的创建时契约。** 既有测试 CID 没有正确设备挂载/CDI 配置、已有 `/dev/dri` 范围过宽，或无法隔离用户桌面时，不能直接往运行容器注入、改登记或以私有管理根重建。先交付复用失败证据和最小替代方案；需要新建或更改冻结配置时单独取得该具体操作的授权。

## 4. 产品设计与开发拆分

### 4.1 当前源码的起点

11 月 15 日开工核对与首轮增量；实机通过范围见执行回执：

- 原 `service.py` 将全部 `devices/portals/gpu` 与 `--desktop` 绑定。首轮已允许显式 render node 不依赖桌面，保留 camera/card、自动 `gpu` 与 Portal 的桌面要求；53 项相关离线回归通过。`gpu` 路径仍收集 `/dev/dri` 节点，未改变批量语义，GPU 实际访问仍待验收。
- `runtime.py:creation_argv()` 的设备白名单只接受 `/dev/videoN` 和 `/dev/dri/cardN|renderDN`，尚无 NVIDIA CDI 接入。
- `catalog.py` 将 `devices`、`desktop` 等作为创建契约/替换判定字段，不能为硬件测试绕开。
- `shortcuts.py:target_names()` 仍固定返回三个目标；目录层也有 `PREPARED` 与已实现驱动白名单。
- 发布是 v0.0.7；开发树版本仍为 0.0.7.dev0，`release-baseline.json` 仍是构建 v0.0.7 使用的 v0.0.6 来源记录。开工已与 v0.0.7 发布清单核对，产品树当时仅版本标记不同；本轮继续保留既有脏改动与索引。

### 4.2 实现批次

| 批次 | 设计与允许的增量 | 独立验收重点 |

模块名和 CLI 拼写在 D1 设计审查时确定。拟提供硬件清单、能力报告和显式探针三个职责，不把本文中的职责名宣称为现有命令。硬件支持由设备/驱动/用户空间组合决定，不按发行版 ID 硬编码“支持 GPU”。

设备授权边界首先是环境；同一发行版共享容器中的应用不能仅凭设备选择变量获得独立隔离。`CUDA_VISIBLE_DEVICES`、Mesa/ICD 选择只帮助选后端，不替代设备权限与挂载边界。G02 的实际要求是核对环境获准范围及本次选中设备，不据此宣称同容器应用级 GPU 隔离。

图形探针优先使用 render node 和离屏接口。HD 7470 若缺所需节点或接口，只能评估精确 `cardN` 与另行准入的私有显示；需要抢占 DRM master、切换 VT 或干扰现有点亮输出时保持 BLOCKED，不能接管宿主显示会话。

NVIDIA CDI 路径必须核验受信宿主配置来源、实际挂载/库、精确 GPU UUID 和 OCI hook 冲突；不照抄上游示例中的 `gpu=all`、新建容器或关闭 SELinux 标签。CDI 文档说明 rootless 与 Podman 接入，但本项目还需自己的准入、身份与生命周期实现。[NVIDIA CDI 文档](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/cdi-support.html)

宿主内核驱动由宿主管理；客体装用户空间驱动/运行库。NVIDIA 按工具链与宿主驱动兼容关系处理，AMD/Intel 按实际内核接口和 Mesa/媒体后端处理。不能复制任意宿主库进客体、全局改 `LD_LIBRARY_PATH`、自动安装内核模块或用特权容器补齐缺口。

## 5. 用例与通过标准

以下为验收标准，结果独立记录。2026-11-15 CPU 首轮：C01/C02/C06 在本机宿主/Debian、服务器宿主/Fedora/Arch 通过；C03 在服务器宿主/Fedora/Arch 通过。本机补充轮因内存准入不足 NO_START；服务器 C04/C05 部分验证、C07 未测。随后专用 DRM 轮：Intel / Debian 的 G01、G03 小型离屏路径通过，核对真实 iris 后端、同一 render node 与完整像素读回；AMD / Fedora 的 G01 映射/实际访问与 G03 r600 硬件离屏绘制通过，28 包正式安装及库存验收完成。两端均完整读回 256×256 固定图案；本轮按用户要求收尾后暂停。分别见 CPU 与 DRM 回执，不把宿主快照、节点访问或离屏结果扩大到其他后端。

### 5.1 GPU

| G05 | V100 CUDA | 固定输入拷入/拷出、整数/FP32/FP64 已知答案、同步与错误检查；记录 UUID、SM、编译架构、runtime/driver、实际加载库 |
| G06 | V100 矩阵/混合精度 | 小矩阵乘法核对 CPU 高精度参考和预定误差；需要声称 Tensor Core 时另给实际指令/后端证据；普通 GEMM 成功不自动证明 Tensor Core |
| G07 | 视频硬解 | 固定短片→硬件后端→输出帧；核对尺寸、帧数、格式、色彩与容差；需有本作业可归属的引擎或提交证据 |
| G08 | 视频硬编 | 固定原始帧→硬件编码→独立解码回读；核对可解码性、帧序/数量/尺寸与预定画质容差；编码器名字不是充分证据 |
| G09 | 不支持/回退/错误路径 | 无设备、权限不足、缺 ICD/库、后端不支持、选错卡和软件回退均给稳定原因；以 fake/子进程私有配置构造，不改宿主驱动或权限 |
| G10 | 正式入口与收尾 | Unifier 发起一个计算程序、一个离屏图形程序、一个编解码程序；退出后执行树、GPU 上下文、租约和容器状态有界恢复 |

视频首轮采用有来源与哈希的 H.264 8-bit、YUV420、720p、最多 5 秒素材；原始帧/中间产物总额预先计算。HEVC、VP9、AV1 及更高位深按查询到的 profile 分批扩展，编码与解码方向分开。HD 7470 优先验证可用的旧格式解码，禁止将软件编码包装为专用视频引擎能力。

像素和整数结果优先使用确定性校验；浮点按输入范围预先登记绝对/相对误差。视频有损编码不能要求输出文件哈希等于原件，也不能只要求文件非空；先固定参考帧、色彩转换与质量判据，再执行。宿主与客体不支持同一后端时保留各自功能结果，性能对照标缺失。

本版不把屏幕采集、Portal/PipeWire 或会议远端接收作为上述视频编解码的替代证据。这些原路线图项目继续保留，需独立显示/账号/设备方案后另行验收。

### 5.2 CPU

| ID | 内容 | 两端共用的通过条件 |
|---|---|---|
| C01 | 架构/ISA 准入 | 宿主与客体 ELF、CPUID、OSXSAVE/XGETBV 等操作系统启用状态一致；不把 `/proc/cpuinfo` 标志当实际执行结果 |
| C02 | 已知答案指令 | SSE4.2、AVX/AVX2、FMA、AES-NI、BMI 等按支持逐项执行，核对结果与确实走到相应指令；本机 AVX-512 仅在现场条件满足时单列 |
| C03 | 原子/线程同步/计时 | 有界两工作线程和固定迭代，检查无丢失更新、同步完成与单调时间，不启动全核压力 |
| C04 | 拓扑/亲和性/NUMA | 比较可见 CPU 与实际允许的 affinity/cpuset；有多 NUMA 节点才验证允许节点；可见核数不等于可用配额 |
| C05 | cgroup 资源与退出 | 读取并核验已有 `cpu.max`、`cpu.stat`，短负载确认限制和收尾；该限额契约中的预期节流不当作无限额性能数据 |
| C06 | 跨代可移植性 | 基线二进制不依赖本机 `-march=native`；ISA 专用函数先检测再分派，服务器缺少的扩展安全拒绝；不得用本机 AVX-512 构建覆盖服务器 |
| C07 | PMU | 仅在当前权限可用时观测本轮目标进程；无权限记录受限，不修改全局 `perf_event_paranoid`，不阻断基础 CPU 功能结论 |

Xeon 的插槽数、核心数、NUMA 和启用扩展以现场为准，不按型号补造。CPU 功能测试同时保留标量参考；容器共享宿主内核，不承诺为缺少的指令提供模拟。XSTATE 的可执行条件参照 [Linux XSTATE 文档](https://docs.kernel.org/arch/x86/xstate.html)。

## 6. 执行顺序与预算

| 阶段 | 工作 | 离开条件 |
|---|---|---|
| H0 基线与设计 | 对齐 v0.0.7、核验三目标基础门槛；逐机硬件/实例/驱动/设备/温度/既有负载清单；确定适用单元与预算 | 每个必测单元有实例、输入、后端、答案、预算与恢复方案；未知项明确阻断 |
| H1 离线实现 | D1→D2→D3，随后 D4/D5；按相关模块走 T1 统一保护器；模拟身份变化、预算中止、缺能力和旧记录 | 定向契约通过，独立审查差异；没有未解释的设备范围扩大 |
| H2 本机首轮 | CPU→Intel 设备→离屏图形/计算→H.264 解码→编码→正式入口退出；Debian 主测后 Arch 代表复核 | 有效结果、独立 GPU 保护与进程收尾；失败或保护中止按规则结束该阶段 |
| H3 服务器首轮 | 上线后重新准入；CPU→HD 7470 设备/GL/可用解码→单张 V100 小算例→矩阵；第二张 V100 串行复核 | 无需桌面完成 CUDA；精确选卡、旧 AMD 边界与两端 CPU 有结果；无外来作业受影响 |
| H4 补项与短对照 | 支持的其他 profile/后端、另一客体代表单元；条件满足再做宿主对照 | 能力矩阵完整，结果可归属；不支持、受限、未测分别列出 |
| H5 发布候选与交接 | 相关回归、独立候选构建/验包、支持矩阵、已知缺口与 v0.0.9 接入说明 | 满足第 9 节；部署仍作为单独动作，不由计划或测试结果代替 |

H-S 已上线，未执行的必测正向项保持 NOT_RUN/BLOCKED，不能从本机结果推导通过。用户本轮已明确批准方案中的两个 Intel/AMD 实例及 AMD 单节点临时 ACL，并根据查询实测批准适当增加服务器监督及本轮临时客体预算。该授权不扩展到 V100/CDI、Arch GPU 或其他宿主变更；本计划本身不授予额外新建许可。

### 6.1 CPU/RAM 与执行保护

- T1 使用 `tools/offline_test_guard.py`：512 MiB、96 任务、1 CPU、swap 0、每批最多 300 秒，独立监督器另计预算。
- 实机首轮沿用项目总额：负载及控制/显示/转发合计最多 1 GiB RAM、128 MiB swap、256 任务、1 CPU；已有实例更小限额照用。两工作线程仍在总 1 CPU 配额内。
- 每台宿主至少保留 1 GiB MemAvailable，并计入尚需新增预算、监督器和余量；连续 15 秒准入、250 ms 监测、PSI/内存/任务数中止均按现行规范。服务器资源多不自动增额。
- 原生对照与客体阶段串行，整棵进程树与容器 scope 均须受保护；单用例通常最多 120 秒，每阶段最多 45 分钟。远端保护器在远端独立运行，SSH 断开后不能留下无人监管负载。
- 下载上限每阶段 200 MiB、额外写入/解包 1 GiB，日志每命令 20 MiB、每轮 200 MiB。CUDA/编译工具若超出，优先复用已核验版本或小型可审计预编译探针；不得自动下载完整 SDK/大镜像。缺依赖时另列来源、大小和安装方案。

### 6.2 GPU 额外保护

CPU/RAM cgroup **不提供通用的 GPU 显存、执行时间或功耗硬限额**。本版探针必须控制输入尺寸、总分配、循环和提交次数，并验证自身退出；监测只能发现问题，不能冒充 GPU 硬隔离。

- 初轮单张卡、单队列、一个小任务；显式设备分配上限 128 MiB，单次 kernel/绘制/编解码提交以短样本起步，每次任务最长 10 秒。上述是探针参数上限；上下文、驱动缓存和隐式分配另计，不能声称实际显存被硬限在 128 MiB。
- 离散 GPU 先核对实际总显存、已有占用与上下文开销，预留至少 25% 总显存且不少于 128 MiB；没有可证明的余量或无法约束输入就 BLOCKED。核显共享内存也计入宿主准入，不能当独立免费显存。
- 执行前登记 GPU 温度/驱动温度阈值、散热条件与现有作业；首轮建议 GPU 中止线不高于 70°C、CPU 不高于 80°C，且低于实际厂商临界线留出余量，具体传感器和最终阈值写入当轮方案。指标无法读出时不开展该设备的持续负载；低负载身份查询与计算验收分别处理。
- 历史 V100 风扇接口与 Linux PWM 映射未确认，故在现场核对散热与监测前不开始计算负载。本版不调整风扇曲线、功率上限、时钟、持久模式、内核驱动或宿主会话。
- 用户模型服务可能占用 V100。不能停止它腾卡，也不能将同卡服务的温度/利用率归因于本作业；设备不可用时等待空闲/安排合适窗口。多张 V100 逐张核验，不默认独占整机。
- 无已知安全边界的长 kernel、不受控厂商 benchmark 和故意 GPU hang 不执行。出现设备重置、驱动错误、超时或无法收回上下文时停止后续动作，记录精确对象；不自动 GPU reset、卸载模块或重启宿主。

### 6.3 对照方法

仅在功能用例通过且无保护事件后启动。相同设备、输入、二进制/库版本、后端、时钟策略和可比预算；原生端也使用私有数据与资源保护。小样本只报告原始耗时和差异，正式统计遵循本机测量规范的有效样本数与配对要求。显存、主存、CPU 时间、GPU 执行时间和编解码吞吐分开报告，不用两台不同机器的速度差作为容器开销。

## 8. 结果与证据格式

每轮使用 `artifacts/v008-hardware-<host>-<time>-<random>/`，至少提供：执行前方案、主机/设备/客体指纹、源码与二进制哈希、输入清单、用例台账、预算与采样、原始退出码、输出校验、收尾/恢复记录及简短报告。私有身份材料不混入可公开日志。

结果按两个维度表达：

1. **能力**：`available / unsupported / restricted / unknown`，带原因、来源及适用的型号/驱动/API/profile。缺工具、离线、权限不足或证据不完整不能写成硬件不支持。
2. **执行**：沿用 `PASS / FAIL / PARTIAL / NOT_RUN / BLOCKED / UNKNOWN / INVALID`；尚未执行保持 NOT_RUN。已证实不支持时，正向用例记 NOT_RUN 并注明“不适用”；其明确拒绝/回退诊断另立负向用例，可独立 PASS。

建议每条结果包含 `case_id`、`host_id`、设备 PCI/UUID、`target/CID/generation`、`code_fingerprint`、`backend/version`、`capability_state`、`result`、`reason_code`、`oracle`、`budget`、证据路径及 `cleanup_state`。能力查询、算例成功、真实应用和性能结果不合并成一个 GPU supported 布尔值。

暂定原因类别：设备不存在、权限拒绝、驱动/库缺失、工具链不兼容、后端不支持、错误设备、软件回退、资源准入失败、散热未核验、退出状态未知。最终稳定编码由 D1 定义，本文不新增现有产品 API。

## 9. v0.0.8 完成与发布条件

- C-L 与 C-S 完成 C01–C06 的适用项；缺少某条 ISA 的明确拒绝有效，不因此宣称该 ISA 已执行。
- Iris Xe 完成设备、GL/Vulkan、一个 GPU 计算后端、至少一个支持格式的硬解与硬编、正式入口收尾。
- V100 完成无桌面精确选卡、CUDA G05/G06 与退出；每张纳入本版清单的物理卡都有身份与小算例结果。Tensor Core 未独立证实时必须保留该项未验证。
- HD 7470 完成身份/权限、硬件 GL、可用解码与软件回退/不支持项诊断。若宿主驱动本身缺少解码后端，记录 restricted/unsupported 的证据和范围，不能假装客体解码通过；实际故障也不能降格为不适用。
- Debian、Fedora、Arch 至少各有本计划分配的代表单元；每项声明附具体机器、驱动、后端与范围。服务器离线造成的必测空缺使整个专项保持 PARTIAL，不能发布为三类 GPU 全验收。
- D1–D5 的离线契约、旧数据兼容与候选验包通过；openSUSE 仍拒绝创建；日常数据、原索引与历史回执保全。
- 已纳入的关键缺陷有最小复现、修复后回归和相应的真实工作流证据。仍受准入或环境限制的测试明确记录，不计入通过。
- 所有本轮执行和 GPU 上下文有界结束，原实例状态恢复或明确披露；没有未处理的身份不明对象/恢复屏障。
- 支持矩阵区分“通过、硬件/后端不适用、待外部条件、未测、失败”；PMU、多卡并行、图形显示/会议、游戏与长时结果不得暗含在本版承诺中。

本文件完成只表示范围、设计、顺序和验收条件已确定。代码实现、离线回归、硬件实测、候选构建与日常部署分别报告。
