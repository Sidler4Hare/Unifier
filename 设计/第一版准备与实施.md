# 第一版准备与实施

范围确定日期：2026-10-18，Asia/Shanghai。

第一版只使用 **Debian 13、Fedora 44、Arch Linux 当前滚动版**。其他发行版的资料保留为比较背景，不进入本轮模板、工作量或验收矩阵。

## 1. 本轮准备的实验基础

在现有 Fedora 44 宿主上准备三套 x86_64 用户空间，全部共用宿主内核。三类宿主的对称性测试在后续阶段执行。

| 标识 | 目标 | 官方镜像来源 | 原生后端 |
|---|---|---|---|
| `debian13` | Debian 13 最小用户空间 | `docker.io/library/debian:13-slim` | APT / dpkg |
| `fedora44` | Fedora 44 基础用户空间 | `registry.fedoraproject.org/fedora:44` | DNF / RPM |
| `arch` | Arch 当前发布的滚动基础镜像 | `docker.io/library/archlinux:latest` | pacman / libalpm |

Debian 的 slim 模板保留原生包管理，用于先测最小基础成本；它不等于完整桌面安装。Arch `latest` 对应当前发布的 base 镜像，不承诺该镜像内每个包与查询瞬间的滚动仓库完全同步；后续首次安装包时执行完整升级并记录新的包集合。

来源已核对：[Debian 官方镜像](https://hub.docker.com/_/debian)、[Arch 官方镜像](https://hub.docker.com/_/archlinux)。Fedora 镜像通过 Fedora 自有 registry 实际查询、解析和平台核对，结果保存在镜像锁文件。

## 2. 可复现的镜像身份

目标声明：[targets.toml](../config/targets.toml)。锁文件：[images.lock.json](../config/images.lock.json)。

锁定规则：

1. 从明确的官方镜像标签获取原始 manifest 或 index。
2. 对多架构 index 选择唯一的 `linux/amd64` 普通镜像，排除其他架构及 attestation 条目。
3. 记录源 manifest 摘要与选中的平台 manifest 摘要。
4. 使用 `repository@sha256:...` 重新核对目标平台和摘要。
5. 三个目标全部成功后，才原子替换锁文件；后续拉取和启动均使用锁定引用。

`lock` 默认保留现有锁。只有显式 `lock --refresh` 才解析新的镜像；Arch 更新同样经过这个入口。digest 用来固定内容身份，镜像来源信任和原生包仓库验证另有各自职责。

Arch 的安装/更新适配器必须维持整套仓库状态，例如使用 `pacman -Syu --needed <packages>` 完成全量升级与安装，不能使用 `pacman -Sy <package>`。官方镜像还提示本地签名密钥初始化问题；首个可写环境的安装验收需要覆盖 keyring 初始化，保留包签名检查。[Arch 镜像更新及 keyring 说明](https://hub.docker.com/_/archlinux)

## 4. 准备命令与检查边界

在项目根目录执行：

```bash
python3 tools/lab.py doctor --output evidence/lab-preflight-current.json
python3 tools/lab.py lock
python3 tools/lab.py pull --output evidence/lab-pull-current.json
python3 tools/lab.py smoke --output evidence/lab-smoke-current.json
```

需要刷新镜像时，先执行 `python3 tools/lab.py lock --refresh`，再拉取并重做探针。`smoke` 使用本地锁定镜像和 `--pull=never`，不会在测试时自动换成新标签。

基础探针依次检查：

- `/etc/os-release` 与所选目标及版本一致。
- `uname -r` 与宿主一致。
- `keep-id` 下的 UID/GID 与宿主用户一致。
- 各自原生包管理入口存在，能查询包数据库，并导出完整包清单。
- 同一个实验目录以相同绝对路径进入三个环境。
- 容器读到的宿主输入校验值一致，写回文件由宿主用户拥有。
- 三个环境依次追加的共享文件，宿主能读取并核对顺序。

探针为临时容器，完成后退出并删除；保留基础镜像、证据和 `.lab/runs/` 中的实验输入输出。它不启动完整 init，不执行安装或更新事务，根目录只读，网络关闭。共享目录仅为本项目创建的实验目录。

SELinux 标签只在这些实验目录上使用共享的 `:z`，保持宿主 Enforcing。该用法依据 [Podman 卷标签说明](https://docs.podman.io/en/latest/markdown/podman-run.1.html#volume-v-source-volume-host-dir-container-dir-options)；后续用户文档目录的接入策略仍需专门实现和验收。

契约检查：

```bash
python3 -m unittest discover -s tests -v
sh -n fixtures/lab-smoke.sh
```

这些检查防止错误平台、浮动标签替换锁定引用、发行版或内核身份不符、错误文件内容或 UID/GID，以及误以 root 运行准备流程。

## 5. 第一版的实现边界

第一版形成一条完整路径：**创建环境 → 原生安装应用 → 统一启动 → 共享文件读写 → 原生更新/卸载 → 停止环境并核对状态。**

初始技术选择：

| 部分 | 选择与理由 |
|---|---|
| 管理核心 | Python 3.11+，优先标准库；便于检查原生包管理结果和记录事务 |
| 执行后端 | rootless Podman；已有运行时承担 namespace、容器进程和文件层管理 |
| 环境复用 | 每个发行版目标默认一个共享应用环境；依赖冲突再增加实例 |
| 运行模式 | 普通应用环境起步，完整 init 作为后续明确选择 |
| 文件视图 | 环境系统状态独立；文档和工作目录按明确挂载保持原路径 |
| 启动方式 | 结构化 argv；保留工作目录、退出码、信号及来源信息 |
| 身份与状态 | 独立环境 ID、镜像身份、包清单、导出入口和事务记录 |
| 宿主集成 | 宿主提供桌面、音频和设备能力，接口逐项接入 |

不会在第一版引入普遍的跨发行版动态库混装或逐包脚本翻译。三套原生包管理器分别维护自己的根目录与状态。

## 6. 数据与适配接口先固定什么

环境记录和运行时适配器已由 `src/multilinux/` 实现，见第 10 节。发行版适配器和事务记录已实现，见第 11 节。启动记录已实现，见第 12 节。资源采样已实现，见第 13 节。

**环境记录**至少包含：环境 ID、发行版标识、目标版本/滚动轨道、CPU 架构、基础镜像摘要、当前可写修订、内容修订、运行状态、包清单校验值、共享挂载、网络模式和创建/更新时间。可写修订是容器 ID，包事务不更换它。内容修订从 1 开始，包清单校验值变化时加一。Arch 的镜像版本、仓库更新时间、包集合校验值和 keyring 初始化时间分别记录。

**发行版适配器**提供：查询包状态、安装本地包或仓库包、更新、卸载、导出包清单、解释原生错误。APT、DNF、pacman 的关系与版本比较留给原生工具；统一层不假定三者的事务阶段相同。Arch 的安装和更新维持整套仓库状态，使用 `pacman -Syu`，并保留发行版默认的签名检查。

**运行时适配器**提供：创建、检查、启动、执行 argv、停止、导出、删除本项目所属环境，以及供资源采样使用的容器大小和镜像信息。资源采样由 `ResourceProbe` 实现。所有资源用环境 ID 和项目归属标签定位，避免按模糊名称批量操作其他容器。

**事务记录**至少包含：事务 ID、环境 ID、目标操作、执行前修订、原生工具结果、验证结果、宿主入口变化、完成或失败阶段。记录保存在 `.lab/state/transactions/`，删除环境不会删除它们。用户文档和外部数据库的变化不纳入根目录快照的回滚承诺。

**启动记录**保存在 `.lab/state/launches/`。删除环境不会删除这些记录。每条记录包含应用 ID、所属环境、可执行文件、argv、工作目录、合并后的环境变量和会话挂载；导出后还保存桌面文件路径、文件类型和导出前的 `mimeapps.list`。共享目录里的可执行文件通过所属环境启动，使用该环境的加载器和库。

## 10. M1 生命周期结果

2026-10-19 15:27:10–15:28:04 +08:00，在当前 Fedora 44 宿主上用锁定镜像创建了三个临时环境。检查完成后容器和状态记录都已删除；`writable_revision` 是当时的容器 ID，不能再用来启动。

入口是 `python3 tools/ml.py`。每个环境是一个 rootless Podman 容器：可写根目录、默认 `--network=none`、没有完整 init。本节 M1 使用 rootless 默认用户命名空间，因此环境里的 root 写到共享挂载上的文件属于宿主用户。2026-10-22 增加可选 `--userns keep-id` 和应用的 `--as-host-user`，将包管理的容器 root 与 GUI 的宿主 UID/GID 分开。容器名包含项目路径摘要。启动、执行、停止和删除都只作用于标签同时等于本项目路径、该环境 ID 和 `environment` 角色的那一个容器。

```bash
python3 tools/ml.py env create --target debian13
python3 tools/ml.py env start debian13
python3 tools/ml.py env run debian13 --workdir /usr -- true
python3 tools/ml.py env stop debian13
python3 tools/ml.py env remove debian13 --yes
```

`run` 只在环境已经启动时执行。`--` 后面的参数作为 argv 传入，退出码是该进程的退出码。宿主环境变量默认不传入；要用 `--env KEY` 逐个点名。创建时环境处于停止状态。`create` 会先启动一次，核对发行版、`x86_64`、宿主内核并导出排序后的原生包清单，然后再停止。身份或清单检查失败时删除刚创建的容器，不留下记录。

| 检查 | 结果 |
|---|---|
| 创建后的身份 | Debian 13、Fedora 44、Arch rolling 均与目标一致，创建结束时为 stopped |
| argv、工作目录、退出码 | `true` 为 0，`false` 为 1，`sh -c 'exit 17'` 为 17；`--workdir /usr` 时环境内 `pwd` 为 `/usr` |
| 环境来源 | Debian 写入 `/var/tmp/ml-origin` 的 `debian-only` 在 Fedora 和 Arch 中不存在；Fedora 写入自己的标记后，Debian 仍读到 `debian-only` |
| 停止后再启动 | 停止后 `run` 被拒绝；再次 start 后 `true` 返回 0；重复 stop 仍是 stopped |
| 共享文件 | 同一绝对路径挂载中的 `owned.txt` 内容为 `hi`，UID/GID 为 `1000:1000` |
| 包清单 | Debian 78、Fedora 147、Arch 137。按行排序后的 SHA-256 与 M0 探针清单一致 |
| 内核 | 三个环境都是 `7.2.7-200.fc44.x86_64`，与当时的宿主内核相同 |

### 13.1 采集接口与实验身份

产品入口新增 `ml.py res sample` 和 `ml.py res series`。单次采样读取容器 cgroup v2 的 `memory.current`、`memory.peak`、`memory.stat`、`memory.events`、swap、pressure、`pids.current` 和限制值；逐个进程读取 `/proc/PID/smaps_rollup` 并汇总 PSS；conmon 通过 Podman `State.ConmonPid` 单独记录。停止的环境没有 cgroup，相关字段保持 `null`，原因写入 `errors`。磁盘记录 Podman 的 `SizeRw` 和 `SizeRootFs`，以及 `podman system df -v` 中属于本镜像和本容器的行。宿主侧记录可用内存、swap、load 和 CPU/memory/io PSI。

当前内核接受写 `memory.peak`，但写入 0 后数值不下降。`res series --reset-peak` 和更新实验都会如实记录这一点，不用 0 填补缺失值。更新实验因此在安装与更新之间停止并重启环境，让第二阶段使用新的 cgroup，`memory.peak` 只覆盖该阶段。

同二进制实验使用 `fixtures/resource_probe.c`，以 `-nostdlib -static` 编译成 freestanding x86_64 ELF，不依赖宿主静态 libc。探针读取固定的 4096 字节输入，支持短命令、固定 2000 万次迭代和按时长运行三种模式。证据保存源码 SHA-256、二进制 SHA-256、输入 SHA-256、FNV 输出和构建 argv；三种执行路径的 `result` 输出必须一致。
