# CLI 安装管理页

日期：2026-11-07。这是快捷命令层的一页，不是新的图形安装器。2026-11-08：页面规则不变。新包格式和新派系按 [远期规划](远期规划-2026-11-08.md) 另加，本页不提前拦截宿主自己的包。

## 谁会进入这一页

双击或 `unifier offer 文件` 只在同时满足下面两条时显示 y/n：

- 文件是 Unifier 已准备的包格式：`.deb`、`.rpm`、`.pkg.tar.zst`、`.pkg.tar.xz`、`.pkg.tar.gz`。
- 该格式对应的客体在当前宿主白名单里是跨派系，并且不是宿主自己的包格式。

Fedora 上的 rpm、Debian/Ubuntu 上的 deb、Arch 上的 pacman 包不会进入准备安装，直接交回宿主原来的打开方式。宿主自己的 MIME 类型也不会被登记成 Unifier。白名单之外的格式同样不进入。

## 页面

终端页只有一个问题，空回车不安装：

```
Unifier 安装管理
文件：example.deb
格式：deb
白名单目标：debian13
  y  用 Unifier 安装到对应发行版环境
  n  交给宿主原来的打开方式
选择？[y/n]
```

- `y` 进入现有 `unifier install`。环境没启用或没初始化时沿用原来的拒绝，不在这一页创建容器。
- `n` 启动登记前的宿主处理程序。没有记录时，按已安装的 GNOME Software、Discover、Ark、File Roller 顺序选择。不会再调用 Unifier 自己的 desktop 项。
- `--yes` 和 `--host` 给脚本使用，仍然受上面的白名单约束。`--yes` 不能把宿主自己的包装进 Unifier。

`unifier offer --setup` 只登记外来格式。`unifier offer --remove` 按保存的原处理程序恢复，不改用户数据根和容器。

## 和其他 CLI 页的关系

安装管理页和 `init`、`configure`、`list`、`install` 使用同一套快捷命令：中英文短句、`[y/n]` 或编号、`--json` 不混进进度。底层 `env`、`pkg`、`app` 仍保持英文诊断协议。

后续页面仍按这个顺序长出来，不另做一套全屏界面：

1. 本页决定外来包进入 Unifier 还是回到宿主。
2. `install` 继续负责原生事务、声明依赖和 ELF 补库。
3. `list` / `status` 只查看，不安装。
4. 包事务失败仍走现有 `pkg recover`，不在本页里重试。

本页不处理宿主包数据库、不把解压冒充安装成功，也不把窗口打开写成应用验收。
