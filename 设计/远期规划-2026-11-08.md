# 远期规划

日期：2026-11-08。状态：**准备稿**。本文只排顺序和进入条件。它不修改白名单，不增加可运行目标，不授权拉取镜像、新建容器、包事务或桌面操作。实机仍先读 [全项目测试禁令与规范](../docs/测试禁令与规范.md)。现行客体仍是 Debian 13、Fedora 44、Arch。

架构基线仍是 [2026-10-23 定档](Unifier-架构实验定档-2026-10-23.md)：宿主掌握数据，原生包管理器负责依赖，一个发行版一个日常容器。宿主关系仍是 [派系白名单](发行版派系白名单与容器关系-2026-10-28.md)。可以描述的目标不等于可以创建的目标，这道门继续留在 `resolve_target_contract()`。

## 1. 总顺序

1. **近期**：把 Debian 13、Fedora 44、Arch 做完。做完的定义在第 2 节，不含游戏，也不含新发行版。
2. **发行版**：Alpine → openSUSE → Nix 决定点 → Void → Gentoo → SteamOS → Android。
3. **与发行版并行、但不插队实机的三条线**：性能测量、易用性、CPU/GPU 通路。游戏放在 GPU 通路有证据之后。
4. 每一段都是先离线契约，再单独授权的实机。新容器预算默认为 0。

Nix 放在决定点，不放进承诺名单。Nix 的包管理器可以装进已经准入的客体；NixOS 作为一整个系统是另一件事。决定点之前不写 Nix 驱动，也不加 NixOS 目标。

## 2. 近期：三个现有目标

“做好”指下面六条都有本分支上的证据。缺一条，发行版扩展就停在文档和离线描述。

| 门槛 | 现在 | 做完的样子 |
| --- | --- | --- |
| 停止态清单 | Debian/dpkg 有一条固定 CID 的只读等价。Arch/pacman、RPM 仍是 `unsupported` | 三个目标都能在不启动容器的情况下读出与原生查询一致的清单。读不了的同伴继续让正式包事务在写入前拒绝 |
| 包事务 | apt、dnf、pacman 驱动已有。中断、恢复和正式入口的真实覆盖不齐 | 三个目标各自完成安装、升级、删除、本地包和一次中断后的恢复。退出码 0 与维护脚本失败分开 |
| 同管理根 | 固定 Debian 与 Arch 不在同一管理根。同根多环境被阻断 | 至少两个跨派系环境在同一管理根里共存，包写入不会读错另一套数据库 |
| 实机保护 | PRE03 只有 Debian 上的最小启动、执行、停止 | 被测进程树有聚合预算、独立监测和期限。宿主保留线维持 1 GiB。日常容器 FreeCAD 与腾讯会议不进入测试 |
| 用户路径 | `unifier init` 能选这三个目标。v0.0.4 会把选定入口写入软件列表，不改文件默认打开方式 | 每个目标有一条路径：选择、安装、出现在软件列表、启动、退出。本机是 Fedora，Fedora 客体按同派系规则不能在本机跑，这条路径留到非 Fedora 桌面宿主 |
| 失败边界 | ELF 自动补库覆盖三条驱动的一部分。外部命令、运行时 dlopen、符号版本仍应拒绝或标为未验证 | 缺库、签名、索引和网络失败各有稳定原因。不把补库成功写成应用可用 |

这六条不含：投影的严格快照、ACL/xattr、通用 IDE、跨宿主完整应用、长时 GUI 浸泡、游戏、其他 CPU。那些留在后面的轨道，不拿来否定三目标已经做完。

本机 Fedora 上，`.rpm` 是宿主自己的格式，双击继续交回宿主。Debian 的 deb 和 Arch 包才进入跨派系安装页。这个行为在三目标阶段保持不变。

## 3. 发行版扩展

扩展时沿用现有字段：派系、libc、布局、包驱动、包格式、运行后端、更新策略。新 ID 要显式写入，不能靠 `ID_LIKE` 继承。同派系容器继续禁止。每个新客体先锁定一个版本或一个明确的滚动策略，并单独做镜像摘要。

宿主准入和客体目标分开。某个发行版可以先只做客体。Alpine 即使做成客体，也不因此变成可运行宿主。

### 3.1 Alpine

第一个扩展客体。它带来的是 musl 和 apk，不是另一套 glibc。

第一刀只做一个带版本号的 Alpine，不做 `latest`，不做 Alpine 宿主。`resolve_target_contract()` 里面对 `libc == glibc` 的总闸改成按目标放行：只有这个 Alpine 目标允许 musl。其他未实现的 musl 描述仍然拒绝。

要新写的是 apk 驱动、停止态 apk 清单、以及用户态探针：Python 3.11+、`C.UTF-8`、基础命令是 GNU 还是 busybox。ELF 自动补库现有 apt-file、dnf repoquery、pacman -F，没有 apk 对应物；Alpine 上缺这一条时明确拒绝，不借用别的驱动。

桌面和游戏不作为 Alpine 的通过条件。它先证明命令、包和文件路径。

### 3.2 openSUSE

第二。glibc、FHS、RPM 文件头已经能认出，安装命令必须是 zypper，不能复用 dnf。查询可以走 RPM 库，但停止态 RPM 清单要在三目标阶段先做完，openSUSE 才能开始实机包事务。

第一刀只做 openSUSE Leap 的一个版本，更新策略用已经实现的 `versioned-release`。Tumbleweed 是滚动更新，账本更接近 Arch，单独开一轮。SLES、SLED 保持宿主 ID，不做客体。MicroOS、Aeon、Kalpa 继续按事务式系统拒绝。

同一份 `.rpm` 不能再默认只交给 Fedora 44。Fedora 与 openSUSE 同时存在时，路由必须让调用方选择目标。文件头分不出厂商。在 Fedora 宿主上，`.rpm` 仍是本族格式，不因为多了一个 SUSE 客体就拦截宿主自己的 rpm。

### 3.3 Nix 决定点

默认结论：**不做 NixOS 目标**。在 Debian、Fedora、Arch、以及以后的 Alpine、openSUSE 里安装 nix，是那个客体的普通包。产品不管理 `/nix` 代际，也不把布局改成 `nix-store`。

只有下面任一需求被单独提出时，才重开这一项：

- 用户要的是 NixOS 本身，而不是 nix 命令。
- 系统更新必须是 `generation-switch`，不能是原地升级。
- 宿主就是 NixOS，需要一套不同于现行白名单的准入。

重开之前不写 nix 驱动，不加镜像锁。

### 3.4 Void

第四。词表里已有 xbps。Void 同时有 glibc 和 musl 两种根，还有 runit，没有 systemd。维护脚本里已经把“不是 systemd 作为 pid 1”记为可识别情况，不能把它当成安装失败。

第一刀只做 **glibc Void** 的一个锁定镜像。musl Void 放到 Alpine 的 musl 路径已经稳定之后，避免两条 musl 线同时开。XBPS 的签名、清单锁和升级语义单独写，不借用 pacman。

### 3.5 Gentoo

第五。更新策略词表里的 `source-build` 尚未实现。容器里完整编译会吃满 CPU、磁盘和时间，和现行资源预算冲突。

第一刀是一个固定 profile，优先使用官方二进制包。产品命令不提供无边界的 `emerge` 世界升级。源码构建若要做，必须有单独的时间、磁盘和 CPU 预算，并在当次授权里写明。profile、init 和 USE 组合不自动扩展。

### 3.6 SteamOS

第六，而且它不代替游戏测试。游戏在第 7 节，用已经做好的客体测。

SteamOS 3 是 Arch 用户空间加只读根和原子更新，会话层是 gamescope。按现行规则，原子和事务式宿主不能借 Arch 派系放行。因此：

- SteamOS **宿主**要单独的部署档案，不能当成 Manjaro 那种 Arch 派生。
- SteamOS **客体**若要做，是一个锁定镜像加会话差异，不是第七套包管理器。
- 只为了跑游戏时，不创建 SteamOS 目标。Arch 或 Debian 客体加上宿主 GPU 就够开始测量。

### 3.7 Android

最后，并且是另一条运行时，不是第四个 Podman 发行版。词表里已经留了 `bionic`、`android-system`、`android-apk` 和 `android` 运行后端，都还不能创建。

Android 应用不经过 apt、dnf、pacman，也不共享这些发行版的 FHS。以后的方案要单独选：兼容层、Android 容器，或模拟器。选择之前不把 Android 写进 `targets.toml`。通过条件至少包括应用安装、显示、输入和存储边界，与桌面发行版的 GUI 验收分开。

## 4. 性能

现在没有一张能说明卡顿来源的测量。有些应用偶尔卡顿，只作为待查现象。普通共享项目走直接 bind，不走 FUSE；只读 FUSE 只浏览已停止的环境。每次属性重验证会使普通文件页面失效，这个成本还没量化，它解释不了日常应用交互卡顿，除非证据指到投影路径。

先测量，再改代码。同一应用、同一数据和同一动作，记录客体与宿主直跑的差异。宿主没有同款程序时，对照标为缺失，不用另一个客体冒充宿主。

测量分开四段，不混成一个“性能分数”：

| 段 | 看什么 |
| --- | --- |
| 冷启动 | 从命令到窗口可输入，或到 CLI 打印首行 |
| 稳态交互 | 输入到画面更新。没有帧时间就不报卡顿百分比 |
| 保存 | 写入已绑定的宿主目录，对一次 fsync 或应用自己的保存完成 |
| 容器内写 | 装包、写客体自己的 `/usr` 或家目录。这走容器写层，不代表绑定目录的速度 |

优先核对的运行路径，按现有代码已经存在的开关：

1. 是否把 `/dev/dri` 交进客体。`gpu` 只在 `--desktop` 时挂上显卡节点。没挂上时，图形应用会落回软件渲染，这足以造成间歇卡顿。
2. Wayland 或 X11 往返、门户和音频是否在这条应用的启动路径上。
3. 卡顿发生时写的是绑定目录，还是容器内部文件。
4. 测试用的内存和进程数上限只约束测试进程。不把测试预算误当成日常容器的限制，也不为了测流畅而放宽 1 GiB 宿主保留线。

未经过同一方法的前后对比，不改调度、不改挂载、不加缓存层。用户没有确认通过线之前，不设帧数或毫秒门槛。

## 5. 易用性

易用性保持纯 CLI 和“一个发行版一个容器”。不恢复已经否决的图形安装页，不把 UUID、CID 和代际交给用户选。

近期就值得做的四件小事，都不依赖新发行版：

1. **一句话状态**。环境是停着还是在跑，上次失败是策略拒绝、包事务、还是应用自己退出。策略拒绝和安装失败继续分开。
2. **失败后只有一个下一步**。该恢复、该看缺库、还是该停止，命令在失败输出里给出。不要求用户先读诊断手册。
3. **图形是否在用软件渲染**。能看出来客体有没有拿到渲染节点。这是性能和游戏的入口，也是用户能理解卡顿的原因。
4. **目标列表来自目录**。`init` 的候选、帮助文本和“恰好三个目标”的校验改成读同一份已实现目录。加 Alpine 时不再改多处硬编码。

v0.0.4 的软件列表保持现状：安装成功并选定入口后写入宿主菜单；包自己标成隐藏的入口不进菜单；不改文件默认打开方式。菜单写失败只让本次安装命令失败，不回滚已经完成的包事务。

## 6. 其他 CPU 和 GPU

现行契约是 `linux/amd64`，宿主检查要求 Linux x86_64。这台机器上的三目标做完之前，不增加架构。

CPU 的下一档只排 **aarch64 Linux**。它要单独的镜像锁、身份检查和包架构。不把 macOS 上的 Linux 虚拟机算成 aarch64 宿主验收。RISC-V 不排期。

GPU 先做本机这一张卡的通路，不排多厂商矩阵：

1. 只读确认渲染节点是否进入指定客体，以及程序看到的是硬件驱动还是软件渲染。
2. 一条不需要账号的绘制探针，记录退出码和驱动名。
3. 之后才把同一探针放到第 4 节的帧时间或启动时间里。

根less Podman、SELinux 和显卡节点权限失败时，结果记为通路未建立。不用 `--privileged` 或放宽设备规则换一次通过。核显和独显不合并成“有 GPU”。第二张卡或第二台机器另开一轮。

## 7. 游戏

目前没有游戏测试，也没有损耗数字。在第 6 节的渲染通路有证据之前，不报任何百分比。

顺序：

1. **通路**。客体能看见渲染节点，探针报出驱动名。软件渲染要在结果里写明。
2. **一款本地程序**。无账号、可重复、退出后不留线上状态。先放在本机政策允许的跨派系客体上（Debian 或 Arch，不是 Fedora 客体）。
3. **对照**。同一程序在宿主直跑和在客体里跑，记录帧时间或完成时间、CPU 和内存增量。宿主没有同款程序时不估算损耗。
4. **兼容层**。Proton、Wine 或 Steam 客户端更晚。它们带来闭源二进制、下载和账号。内核级反作弊和需要宿主内核模块的游戏，预期不能在这个根less 容器模型里运行；这类失败记为模型边界，不记为待修缺陷。

SteamOS 目标的进度不阻塞 1 到 3。游戏通过也不表示 SteamOS 宿主已经准入。

## 8. 进入下一阶段的共同条件

- 上一阶段的门槛有回执，回执写明测试、部署和真实工作流各算什么。
- 新发行版或新架构的实机，每次单独授权。授权写明镜像、CID 来源、资源预算和停止条件。
- 离线测试先证明：新目标能被描述，并且在驱动落地前仍然不能创建。
- 不改两个日常容器的数据根。不删除历史容器来给新目标腾位置。
- 性能和游戏只在有宿主对照或明确写明“对照缺失”时记录数字。

## 9. 本文不改变的规则

- 同派系容器继续禁止，包括 Ubuntu 宿主上的 Debian 客体。
- 原子、事务式、MicroOS、Aeon 不借基础派系放行。
- 默认新增项目容器预算为 0。宿主保留线 1 GiB。
- NixOS、Void、Gentoo、SteamOS、Android 在各自那一节开始之前，保持现在的拒绝或未实现状态。
- 本文不是测试计划，也不是发布说明。三目标的现行证据仍以 `HANDOFF.md` 和对应 `artifacts/` 回执为准。
