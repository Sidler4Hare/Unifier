# 远期规划

2026-11-08 起草，2026-11-19 更新正式版重构与下一版分工。现行客体为 Debian 13、Fedora 44、Arch。实机执行沿用项目测试规范。[全项目测试禁令与规范](../docs/测试禁令与规范.md)

架构基线仍是 [2026-10-23 定档](Unifier-架构实验定档-2026-10-23.md)：宿主掌握数据，原生包管理器负责依赖，一个发行版一个日常容器。宿主关系仍是 [派系白名单](发行版派系白名单与容器关系-2026-10-28.md)。可以描述的目标不等于可以创建的目标，这道门继续留在 `resolve_target_contract()`。

## 1. 总顺序

1. 以已发布的 **v0.0.7** 为基础，开发树先对齐发布清单并保留现有改动。三目标的停止态清单、固定实例包事务及指定写入中断恢复已有 11 月 14 日证据，具体缺口见 [当前状态](../docs/当前状态.md) 与 [剩余台账](../docs/测试剩余工作-20261109.md)。不再把已完成的 Arch 恢复作为新的起点。
2. **v0.0.8 正式版完成 Python 主线重构。** 清理历史实现和重复防御，把通用兼容能力归入桌面协议、客体客户端和设备层，按同一口径核对产品代码净减。三目标日用流程和 CPU/GPU 专项继续按原用例收口，为下一版交付统一的目标目录和驱动接口。[整体重构报告](../docs/整体代码重构报告-2026-11-19.md) · [v0.0.8 硬件与缺陷计划](v0.0.8-硬件专项与v0.0.9准备.md)
3. **v0.0.9 接入 openSUSE Leap 16.1，优化应用内操作的响应与性能，并完成正式开源上线前检查。** 应用内性能以编辑、滚动、模型重算、保存等操作衡量。开源前检查项目及第三方许可、公开文件范围和干净检出构建。到 v0.1.0 前暂定四个客体，其余候选留待后续评估。[openSUSE 适配计划](openSUSE-Leap适配-v0.0.9.md) · [性能样本与开源检查](../docs/整体代码重构报告-2026-11-19.md)
4. 硬件实机仍须复核三目标基础门槛与所选负载保护。功能通过后再做同机性能对照；一般易用性、游戏和长时负载另排，游戏等待 GPU 通路证据。
5. 每一段都是先离线契约，再单独授权的实机。新容器预算默认为 0。

Nix 放在决定点，不放进承诺名单。Nix 的包管理器可以装进已经准入的客体；NixOS 作为一整个系统是另一件事。决定点之前不写 Nix 驱动，也不加 NixOS 目标。

## 2. 近期：三个现有目标

“做好”指下面六条都有本分支上的证据。缺一条，发行版扩展就停在文档和离线描述。

| 门槛 | 现在 | 做完的样子 |
| --- | --- | --- |
| 停止态清单 | 三目标标准停止态实库与原生查询已对齐；运行态一致快照仍拒绝 | 三个目标都能在不启动容器的情况下读出与原生查询一致的清单。读不了的同伴继续让正式包事务在写入前拒绝 |
| 包事务 | 固定实例普通仓库/本地包及指定写入中断恢复已实证；其他写入点和宿主崩溃未覆盖 | 三个目标各自完成安装、升级、删除、本地包和一次中断后的恢复。退出码 0 与维护脚本失败分开 |
| 同管理根 | Ubuntu 原 Fedora→停止态 Arch 的同根观察已通过；运行态与模糊恢复边界仍受限 | 至少两个跨派系环境在同一管理根里共存，包写入不会读错另一套数据库 |
| 实机保护 | 三目标轻量 CLI/合成私有 GUI 已通过；新 GPU、重 GUI 负载需重新准入 | 被测进程树有聚合预算、独立监测和期限。宿主保留线维持 1 GiB。日常容器 FreeCAD 与腾讯会议不进入测试 |
| 用户路径 | 三目标固定实例的私有软件列表安装、启动、退出已通过；完整厂商应用矩阵仍开放 | 每个目标有一条路径：选择、安装、出现在软件列表、启动、退出。本机 Fedora 不运行同派系客体 |
| 失败边界 | 签名、仓库连接、维护脚本与指定中断已有证据；共享提供者升级及加载器/符号等完整实证仍不足 | 缺库、签名、索引和网络失败各有稳定原因。不把补库成功写成应用可用 |

这六条不含：投影的严格快照、ACL/xattr、通用 IDE、跨宿主完整应用、长时 GUI 浸泡、游戏、其他 CPU。那些留在后面的轨道，不拿来否定三目标已经做完。

本机 Fedora 上，`.rpm` 是宿主自己的格式，双击继续交回宿主。Debian 的 deb 和 Arch 包才进入跨派系安装页。这个行为在三目标阶段保持不变。

## 3. 发行版扩展

扩展时沿用现有字段：派系、libc、布局、包驱动、包格式、运行后端、更新策略。新 ID 要显式写入，不能靠 `ID_LIKE` 继承。同派系容器继续禁止。每个新客体先锁定一个版本或一个明确的滚动策略，并单独做镜像摘要。

宿主准入和客体目标分开。某个发行版可以先只做客体。Alpine 即使做成客体，也不因此变成可运行宿主。

### 3.1 Alpine

v0.1.0 后的候选。适配需要 musl 和 apk 两条能力。

第一刀只做一个带版本号的 Alpine，不做 `latest`，不做 Alpine 宿主。`resolve_target_contract()` 里面对 `libc == glibc` 的总闸改成按目标放行：只有这个 Alpine 目标允许 musl。其他未实现的 musl 描述仍然拒绝。

要新写的是 apk 驱动、停止态 apk 清单、以及用户态探针：Python 3.11+、`C.UTF-8`、基础命令是 GNU 还是 busybox。ELF 自动补库现有 apt-file、dnf repoquery、pacman -F，没有 apk 对应物；Alpine 上缺这一条时明确拒绝，不借用别的驱动。

桌面和游戏不作为 Alpine 的通过条件。它先证明命令、包和文件路径。

### 3.2 openSUSE

v0.0.9 的第四个客体。复用 glibc、FHS 和 RPM 文件识别，安装驱动采用 zypper。三目标验收收口后，再以 Leap 实库验证停止态 RPM 清单、隔离和包事务。[openSUSE 适配计划](openSUSE-Leap适配-v0.0.9.md)

首版拟固定 openSUSE Leap 16.1，更新策略用 `versioned-release`。Tumbleweed、SLES、SLED、MicroOS、Aeon、Kalpa 均在本期客体范围之外。

同一份 `.rpm` 不能再默认只交给 Fedora 44。Fedora 与 openSUSE 同时存在时，路由必须让调用方选择目标。文件头分不出厂商。在 Fedora 宿主上，`.rpm` 仍是本族格式，不因为多了一个 SUSE 客体就拦截宿主自己的 rpm。

### 3.3 Nix 决定点

默认结论：**不做 NixOS 目标**。在 Debian、Fedora、Arch、以及以后的 Alpine、openSUSE 里安装 nix，是那个客体的普通包。产品不管理 `/nix` 代际，也不把布局改成 `nix-store`。

只有下面任一需求被单独提出时，才重开这一项：

- 用户要的是 NixOS 本身，而不是 nix 命令。
- 系统更新必须是 `generation-switch`，不能是原地升级。
- 宿主就是 NixOS，需要一套不同于现行白名单的准入。

重开之前不写 nix 驱动，不加镜像锁。

### 3.4 Void

第四。词表里已有 xbps。Void 同时有 glibc 和 musl 两种根，还有 runit，没有 systemd。维护脚本里已经把“不是 systemd 作为 pid 1”记为可识别情况，不能把它当成安装失败。

第一刀只做 **glibc Void** 的一个锁定镜像。musl Void 放到 Alpine 的 musl 路径已经稳定之后，避免两条 musl 线同时开。XBPS 的签名、清单锁和升级语义单独写，不借用 pacman。

### 3.5 Gentoo

第五。更新策略词表里的 `source-build` 尚未实现。容器里完整编译会吃满 CPU、磁盘和时间，和现行资源预算冲突。

第一刀是一个固定 profile，优先使用官方二进制包。产品命令不提供无边界的 `emerge` 世界升级。源码构建若要做，必须有单独的时间、磁盘和 CPU 预算，并在当次授权里写明。profile、init 和 USE 组合不自动扩展。

### 3.6 SteamOS

第六，而且它不代替游戏测试。游戏在第 7 节，用已经做好的客体测。

SteamOS 3 是 Arch 用户空间加只读根和原子更新，会话层是 gamescope。按现行规则，原子和事务式宿主不能借 Arch 派系放行。因此：

- SteamOS **宿主**要单独的部署档案，不能当成 Manjaro 那种 Arch 派生。
- SteamOS **客体**若要做，是一个锁定镜像加会话差异，不是第七套包管理器。
- 只为了跑游戏时，不创建 SteamOS 目标。Arch 或 Debian 客体加上宿主 GPU 就够开始测量。

### 3.7 Android

最后，并且是另一条运行时，不是第四个 Podman 发行版。词表里已经留了 `bionic`、`android-system`、`android-apk` 和 `android` 运行后端，都还不能创建。

Android 应用不经过 apt、dnf、pacman，也不共享这些发行版的 FHS。以后的方案要单独选：兼容层、Android 容器，或模拟器。选择之前不把 Android 写进 `targets.toml`。通过条件至少包括应用安装、显示、输入和存储边界，与桌面发行版的 GUI 验收分开。

## 4. 性能

v0.0.9 的首要问题是用户在已打开的应用里做一个具体动作要等多久。以相同版本和输入对比优化前后的编辑响应、视图更新、模型重算和保存完成时间，同时核对文档或模型结果。下列启动、存储、宿主对照和运行时观察用于定位原因。[应用内性能验收设计](../docs/整体代码重构报告-2026-11-19.md)

现在没有一张能说明卡顿来源的测量。有些应用偶尔卡顿，只作为待查现象。普通共享项目走直接 bind，不走 FUSE；只读 FUSE 只浏览已停止的环境。每次属性重验证会使普通文件页面失效，这个成本还没量化，它解释不了日常应用交互卡顿，除非证据指到投影路径。

先测量，再改代码。同一应用、同一数据和同一动作，记录客体与宿主直跑的差异。宿主没有同款程序时，对照标为缺失，不用另一个客体冒充宿主。

测量分开四段，不混成一个“性能分数”：

| 段 | 看什么 |
| --- | --- |
| 冷启动 | 从命令到窗口可输入，或到 CLI 打印首行 |
| 稳态交互 | 输入到画面更新。没有帧时间就不报卡顿百分比 |
| 保存 | 写入已绑定的宿主目录，对一次 fsync 或应用自己的保存完成 |
| 容器内写 | 装包、写客体自己的 `/usr` 或家目录。这走容器写层，不代表绑定目录的速度 |

优先核对的运行路径，按现有代码已经存在的开关：

1. 是否把 `/dev/dri` 交进客体。`gpu` 只在 `--desktop` 时挂上显卡节点。没挂上时，图形应用会落回软件渲染，这足以造成间歇卡顿。
2. Wayland 或 X11 往返、门户和音频是否在这条应用的启动路径上。
3. 卡顿发生时写的是绑定目录，还是容器内部文件。
4. 测试用的内存和进程数上限只约束测试进程。不把测试预算误当成日常容器的限制，也不为了测流畅而放宽 1 GiB 宿主保留线。

未经过同一方法的前后对比，不改调度、不改挂载、不加缓存层。用户没有确认通过线之前，不设帧数或毫秒门槛。

## 5. 易用性

易用性保持纯 CLI 和“一个发行版一个容器”。不恢复已经否决的图形安装页，不把 UUID、CID 和代际交给用户选。

以下是易用性候选。v0.0.8 只纳入硬件诊断和下一版目标目录准备所需的部分，一般状态/失败流程的整体重做继续后排：

1. **一句话状态**。环境是停着还是在跑，上次失败是策略拒绝、包事务、还是应用自己退出。策略拒绝和安装失败继续分开。
2. **失败后只有一个下一步**。该恢复、该看缺库、还是该停止，命令在失败输出里给出。不要求用户先读诊断手册。
3. **图形是否在用软件渲染**。能看出来客体有没有拿到渲染节点。这是性能和游戏的入口，也是用户能理解卡顿的原因。
4. **目标列表来自目录**。`init` 的候选、帮助文本和“恰好三个目标”的校验改成读同一份已实现目录。加 Alpine 时不再改多处硬编码。

v0.0.4 的软件列表保持现状：安装成功并选定入口后写入宿主菜单；包自己标成隐藏的入口不进菜单；不改文件默认打开方式。菜单写失败只让本次安装命令失败，不回滚已经完成的包事务。

## 6. CPU 与 GPU 硬件验收

本节为硬件长期覆盖清单；**v0.0.8 的具体范围、机器矩阵、开发批次与发布条件以 [专项计划](v0.0.8-硬件专项与v0.0.9准备.md) 为准**。本机 Intel Iris Xe/i5-1135G7 先用合规既有 Debian 13，服务器 V100/HD 7470/E5-2686 v4 等上线并核验后，按派系选择 Fedora 44/Arch；各物理设备串行。V100 以 CUDA 计算为主，HD 7470 按旧 AMD 驱动能力验收，不要求所有 GPU 都支持每个 API。openSUSE 的真实接入留到 v0.0.9。

每个结果绑定宿主 CPU/GPU 型号、内核、运行时版本、设备身份、客体镜像摘要与用户空间驱动版本。下表中的屏幕共享、PMU、虚拟化等不自动成为本版必测项。

### GPU 图形、计算和视频

| 用例 | 通过条件 |
|---|---|
| 设备接入 | 以实际应用 UID 打开获准的 DRM render node，核对宿主 PCI 设备和客体驱动。单列设备缺失、权限拒绝和软件回退。 |
| 图形渲染 | EGL/OpenGL 和 Vulkan 各执行有界离屏绘制，核对实际硬件设备与像素结果。需要桌面显示的用例另在私有会话验证。 |
| GPU 计算 | V100 使用兼容 Volta 的 CUDA 工具链；其他 GPU 按实际提供的 Vulkan compute/OpenCL 后端执行固定小算例。核对选中的设备、提交成功及计算结果。 |
| 视频硬解 | 用固定、可校验的短片在客体执行 VA-API 等原生硬解。首轮选 H.264，后续按驱动报告的 profile 和位深覆盖 HEVC、VP9、AV1 等。逐格式核对帧数、尺寸、画面及实际硬件后端。 |
| 视频硬编 | 用固定原始帧执行原生硬编，记录编码后端和 profile。对输出做独立回读，核对码流可解码、帧数、尺寸和预期画面，按硬件支持分别记录各编码格式。 |
| 应用与屏幕共享 | 分别验证一个真实本地播放应用、一个编码应用和一条 Portal/PipeWire 采集路径。会议的摄像头发送与远端接收使用另行准入的用例。 |

硬编、硬解的通过证据包括应用选定的后端、正确输出，以及可归属到本次作业的视频引擎活动或驱动提交证据。单独记录软件回退和宿主直跑对照。既有 DMA-BUF 导入结果继续只覆盖画面缓冲传递。不同 GPU、驱动和编解码方向逐项验收。[Intel VA-API 驱动](https://github.com/intel/media-driver) · [PipeWire DMA-BUF](https://docs.pipewire.org/1.4/page_dma_buf.html)

### CPU 指令、拓扑和资源

| 用例 | 通过条件 |
|---|---|
| 架构与指令集 | 核对 `uname -m`、ELF 架构、CPUID 和操作系统启用的扩展状态。按实际可用特性分别执行 SSE4.2、AVX/AVX2、FMA、AES-NI、BMI、AVX-512 等小型已知答案用例，核对实际走到对应指令及计算结果。未提供的特性记录为不适用。 |
| 并发原语与计时 | 有界线程数下验证原子操作、同步和单调时钟。记录退出状态、结果一致性和超时。 |
| 拓扑与调度 | 分别核对可见逻辑 CPU、实际亲和性和已有 cpuset 限制，若宿主具备多 NUMA 节点再记录客体所见与允许的节点范围。 |
| CPU 资源隔离 | 在已有 cgroup 预算内观察 `cpu.max`、`cpu.stat`、亲和性及受限作业退出。使用短、有界的负载核对配额和节流，记录受保护的宿主对照。 |
| PMU 和虚拟化 | 按当前权限验证目标进程范围内的 `perf` 事件。KVM/嵌套虚拟化按单独的宿主能力、设备和安全方案评估。权限拒绝或设备未开放分别记录，硬件特性标志仅作为准入证据。 |

现行 CPU 架构为 `linux/amd64`。后续 aarch64 Linux 另立镜像、指令和宿主验收矩阵。RISC-V 暂未排期。[Linux XSTATE](https://docs.kernel.org/arch/x86/xstate.html) · [Linux 性能事件权限](https://docs.kernel.org/admin-guide/perf-security.html)

### 执行约束

先做离线契约，再按 [测试规范](../docs/测试禁令与规范.md) 对每项实机准备允许清单、私有会话和有界作业，串行执行。GPU 和媒体设备按实机专项准入。沿用 rootless、原有权限和至少 1 GiB 宿主保留线，保留保护中止回执。先完成短样本功能验证，再进入性能对照或长时测试。

## 7. 游戏

目前没有游戏测试，也没有损耗数字。在第 6 节的渲染通路有证据之前，不报任何百分比。

顺序：

1. **通路**。客体能看见渲染节点，探针报出驱动名。软件渲染要在结果里写明。
2. **一款本地程序**。无账号、可重复、退出后不留线上状态。先放在本机政策允许的跨派系客体上（Debian 或 Arch，不是 Fedora 客体）。
3. **对照**。同一程序在宿主直跑和在客体里跑，记录帧时间或完成时间、CPU 和内存增量。宿主没有同款程序时不估算损耗。
4. **兼容层**。Proton、Wine 或 Steam 客户端更晚。它们带来闭源二进制、下载和账号。内核级反作弊和需要宿主内核模块的游戏，预期不能在这个根less 容器模型里运行；这类失败记为模型边界，不记为待修缺陷。

SteamOS 目标的进度不阻塞 1 到 3。游戏通过也不表示 SteamOS 宿主已经准入。

## 8. 进入下一阶段的共同条件

- 上一阶段的门槛有回执，回执写明测试、部署和真实工作流各算什么。
- 新发行版或新架构的实机，每次单独授权。授权写明镜像、CID 来源、资源预算和停止条件。
- 离线测试先证明：新目标能被描述，并且在驱动落地前仍然不能创建。
- 不改两个日常容器的数据根。不删除历史容器来给新目标腾位置。
- 性能和游戏只在有宿主对照或明确写明“对照缺失”时记录数字。

## 9. 本文不改变的规则

- 同派系容器继续禁止，包括 Ubuntu 宿主上的 Debian 客体。
- 原子、事务式、MicroOS、Aeon 不借基础派系放行。
- 默认新增项目容器预算为 0。宿主保留线 1 GiB。
- NixOS、Void、Gentoo、SteamOS、Android 在各自那一节开始之前，保持现在的拒绝或未实现状态。
- 本文不是测试计划，也不是发布说明。三目标的现行证据仍以 `HANDOFF.md` 和对应 `artifacts/` 回执为准。
