# 宿主文件进入客体，与文件管理器集成（2026-11-10）

状态：只读审计加方案对比。**本文不授权启动容器、GUI、包事务或新建容器。** 本轮没有改代码，也没有为这个问题动过现场；现场只为钉钉安装被动起停过 `ml-6b061a2f-meeting`。触发问题是用户的原话：想传个文件进客体，找不着往哪传。

## 1. 今天实际可用的通道

按能用的程度排，全部为现场核对结果：

1. **每个环境一条 rw 文档 bind**。Debian 13 日常环境只有 `/home/omg/.local/share/multilinux/documents/wemeet`（`podman inspect` 里唯一一条用户数据 bind，客体同路径，rw）。Arch 环境登记的是 `/home/omg/文档/Unifier-CAD`。这是今天唯一"把宿主文件放进客体应用能打开的位置"的办法，代价是手敲一个隐藏点路径。
2. **新设计的发行版专用文件目录对旧部署无效**。`~/.local/share/unifier/containers/<target>/files` 是 `init` 时显式绑定的新目录；两个日常容器都是承接来的旧部署，`unifier dirs` 自己写着"专用文件绑定：未挂载（旧部署不包含新目录，勿谎报已挂载）"。所以 [CLI 首次配置与发行版专用目录](CLI首次配置与发行版专用目录-2026-10-29.md) 里"用户直接用 `ls`、`cd` 管理专用文件"这条路径对现有日常环境是空的。
3. **`unifier file copy` 结构上正确但当下用不起来**。签名是 `file copy <源根UUID> <源相对> <目标根UUID> <目标相对>`（`src/unifier/cli.py`），两侧都必须先是登记过的 data root。现在登记根只有客体侧那两个文档根，宿主的 `~/下载` 没有登记，所以临时传一个文件要先把源根登记进去。`file list` 为空。这条通道的定位是应用与文件的受控交接，不是用户上传。
4. **`file open`/`file plan` 需要 handler 路由**，`handlers` 登记表当前为 none，provider 只有 `environment-app`，所以"选中一个宿主文件交给某个环境的应用"还没有可用路由。
5. **项目会话与只读投影都不是上传入口**。`project run/shell/session` 解决的是在已接受的项目根里跑客体命令；`view open` 是停止环境的只读浏览，方向反了。
6. **客体里应用的 HOME 不是宿主 home**。以 host-user 启动（两个日常环境都是 `userns keep-id`）时 `home = /home/multilinux-<uid>`（`src/unifier/service.py:778`），那个目录由 `install -d -m 700` 在容器内新建。因此应用文件对话框的默认位置里一个宿主文件都没有，只能手打路径。
7. **宿主侧完全没有入口**。`~/.local/share/kservices5/` 不存在，没有 ServiceMenu 动作，Dolphin 书签里没有相关项，`unifier` 快捷命令里也没有 `put`/发送一类命令（现有命令面：`init configure list dirs path ls install offer run start stop adopt language help`）。`unifier dirs` 与 `unifier path` 只报那个未挂载的新目录，不报第 1 条里真正生效的文档根，这一点是误导性的。

## 2. 宿主 portal 这条路的现状

想"直接用原版文件管理器"（让客体应用弹出宿主的 KDE 文件对话框），一大半已经通了：

- 环境启动时 unifier 用宿主 `xdg-dbus-proxy` 把宿主会话总线过滤后送进容器，白名单里已经有 `org.freedesktop.portal.Desktop`（FileChooser 在这个名字上）和 `org.freedesktop.portal.Documents`（DocumentStore），另有通知、状态栏和 `com.tencent.wemeet.*`。见 `src/unifier/on_demand.py:134-148`，客体内 `DBUS_SESSION_BUS_ADDRESS=unix:path=/run/multilinux-portal/bus`。
- 宿主 portal 在运行，后端齐全：`xdg-desktop-portal-1.22.1`、`xdg-desktop-portal-kde-6.7.5`、`xdg-desktop-portal-gtk-1.15.3`。KDE 原生对话框是可以被调出来的。
- 客体镜像里有 `xdg-desktop-portal 1.20.3`、`xdg-utils`、`xdg-user-dirs` 和 GTK3；`/run/user/1000/wayland-0` 已挂进客体，窗口能上屏。

## 3. 剩下的唯一点：路径可见性，也就是"翻译"

- portal 判断调用方是否沙盒靠 cgroup 与 `.flatpak-info` 一类线索。podman 容器进程在宿主 portal 眼里不是沙盒，于是 FileChooser 返回**宿主真实路径**，例如 `/home/omg/下载/x.pdf`。客体里只有第 1 节那条文档 bind，应用拿到那个路径就打不开。
- 标准沙盒答案（DocumentStore 的 FUSE，宿主侧 `/run/user/1000/doc`）也没有挂进客体：容器只挂了 wayland、X11、pulse、pipewire 四个 socket 和 `/run/multilinux-portal`，`/run/user/1000` 在客体里是自建空目录。
- 同一个问题不止影响对话框。往客体聊天窗口**拖文件**走 Wayland DnD，递过来的是 `text/uri-list` 里的 `file:///home/omg/...`，落回同一个"路径看不见"。所以这不是给某个对话框打补丁能解决的。
- 支持面不齐：走 portal 的才谈得上宿主对话框（GTK3、设了 `QT_USE_PORTAL=1` 的 Qt、Chromium/Electron 的 Open 框）。钉钉的 `Elevator.sh` 设 `QT_QPA_PLATFORM=xcb`，Qt 侧不调 portal 就仍是客体自己的对话框。

## 4. 三条做法

| 做法 | 实质 | 代价与风险 |
|---|---|---|
| 同路径 bind 宿主目录 | 把 `~/下载`、`~/文档`（或整个 `$HOME`）按同路径绑进客体，portal 返回的宿主路径天然有效，**不需要翻译** | podman 不能给已存在的容器加挂载，要重建两个日常容器，牵动 `environment_uuid`/generation 与数据根身份；宿主可见面变大 |
| 真做翻译 | 把 `xdg-dbus-proxy` 换成能读改消息的小 broker：拦 FileChooser 返回，把选中文件复制进该环境已登记的收件根，再把路径或 URI 改写回去 | 中等工作量。语义最干净（客体只见收件夹），但要处理保存回写、多文件选择、权限和中断恢复；可复用 `file_operations`/journal 与受控复制 |
| DocumentStore 正规军 | 让 portal 认调用方是沙盒，走 `xdg-document-portal` 的 fuse，并把 `/run/user/1000/doc` 同路径挂进客体 | 依赖 portal 的沙盒判定细节，要伪造 flatpak 线索，版本行为不可控 |

判断：先用"同路径 bind"验一次最便宜，也最能说明问题；长期正解是翻译 broker。理由是要先确认可见性一旦解决，钉钉、飞书这类厂商应用能否正常打开、保存和拖放——那才是决定要不要做 broker 的依据，现在还不知道。
