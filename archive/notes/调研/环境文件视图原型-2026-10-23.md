# 环境文件视图原型

日期：2026-10-23，Asia/Shanghai。承接[文件层可行性评估](文件层可行性与性能评估-2026-10-23.md)第 8 节的第一个原型：停止后的完整环境根、绝对/相对链接、独立卷、UID/GID、普通文件保存和清理。

结论：**普通宿主进程不能把 rootless 容器的合并根当成目录来浏览。** 合并内容只出现在 `podman unshare` 进入的存储命名空间里。绝对链接在这个命名空间里仍按宿主根解析；要读到容器里的目标，需要以合并根为根再解析。独立卷的数据在宿主上的卷目录，不在停止后的合并根里。通过存储命名空间写入已停止根中的普通文件，容器再次启动后能读到。

这是锁定 Debian 13 基础镜像上的机制实验，不是三发行版验收，也不是文件管理器或产品文件层验收。没有 pull、没有装包、没有改现有容器、没有写 overlay upper 目录、没有改宿主目录标签。临时容器使用 `label=disable`，只为避免这次实验改写标签；这不是产品默认隔离。

## 1. 本机存储

Podman 5.8.9，rootless，原生 overlay（Native Overlay Diff 为 true）。`podman info` 的 graph status 里 **Supports shifting 为 false**。宿主用户 `omg` 的 subuid 是 `524288:65536`。`podman unshare` 里的 uid 映射是：命名空间 uid 0 = 宿主 uid 1000，命名空间 uid 1 起 = 宿主 524288 起。SELinux 为 enforcing。

镜像：`docker.io/library/debian@sha256:918311b7b6c4c6f68b232ba516584925f6c78ad82b6fd534b98979df6438e483`。

## 2. 宿主进程看不到合并根

两次运行都记录到同一条拒绝：

```text
Error: cannot run command "podman mount" in rootless mode, must execute `podman unshare` first
```

`podman unshare podman mount` 成功，路径在 `~/.local/share/containers/storage/overlay/<id>/merged`。冷、热和运行中三次，unshare 挂载命令约 **0.106–0.109 秒**，含 Podman 启动。样本只有这几次，不能写成挂载 SLO。

挂载之后，宿主上的 Python `listdir`/`open` 和 `findmnt` 仍然看不到 overlay：

| 身份 | 宿主看到的 merged | `findmnt -T` | `podman unshare ls` 合并根 |
|---|---|---|---|
| 默认 rootless | 目录可列出，条目数为 0；其下文件 ENOENT | `btrfs`，目标是 `/home` | 有 `bin`、`etc`、`usr`、`var` 等完整顶层 |
| `--userns=keep-id` | 列出直接 EACCES | 命令退出 1，没有文件系统行 | 同样能列出完整顶层 |

`result-unshare.json` 里默认模式的 `host_can_list_stopped_root: true` 只表示空目录 `listdir` 成功。名单是 `[]`。不能把它读成“宿主已经看到发行版根”。

因此文件管理器、宿主 Python 和普通 `cp` 都不能把 `podman mount` 打印的路径当作 `/user/debian`。可用视图要跑在 `podman unshare` 已经进入的那个命名空间里，或由那里面的文件服务把结果提供出来。

## 3. 绝对链接、相对链接和停止后的卷

在合并根里放了 `/var/ml-persistent/os-link -> /etc/os-release`，以及指向容器内 `target/payload.txt` 的绝对链接和相对链接。容器内读到的第一行是 Debian 13 的 `PRETTY_NAME`。

| 读取方式 | `/etc/os-release` 链接 | 容器内绝对/相对链接 | 停止后的 `/var/ml-volume/payload.txt` |
|---|---|---|---|
| 宿主进程直接打开 merged | 文件不存在或 EACCES | 同样不可见 | 不可见 |
| `podman unshare cat`，不换根 | 读到宿主 Fedora 44 的 `NAME="Fedora Linux"` | 未测 | — |
| `podman unshare chroot <merged>` | 读到 Debian 13 | 两者都读到 `container-target` | ENOENT |

相对链接只在 chroot 里核对过。绝对链接的对照已经够用：同一命名空间里，不换根就落到宿主 `/etc/os-release`，换根才落到容器里的 os-release。

卷是另一条路径。容器运行时，`/var/ml-volume` 挂的是 `storage/volumes/<name>/_data`，文件系统是宿主 btrfs。容器停止后，合并根里的 `/var/ml-volume` 是空目录；upper 里的这个目录也是空的。字节在卷目录里：

- 默认 rootless：容器 root 写入的 `volume-payload` 在宿主上属主为 uid 1000，宿主进程能直接读。
- keep-id：容器 root 写这个卷失败（目录在容器里属主是 uid 1000、模式 755）。容器内 uid 1000 写入的 `user-volume-payload` 在宿主上属主也是 uid 1000，宿主进程能直接读。
- 两种模式都由宿主进程向卷目录写入 `host-volume-write`。容器重启后，里面读到了这行字。SELinux 上下文是 `container_file_t`。没有为了写入去做 `chown` 或改标签。

keep-id 还有一个目录权限事实：容器内 uid 1000 创建 `/home/mlview` 得到 Permission denied。容器 root 可以写 `/var/ml-persistent`。宿主用户和容器 root 在 keep-id 下不是同一个磁盘身份。

upper 只含这次写出的差异。默认模式下宿主能读到 `var/ml-persistent/private.txt`，列出的顶层只有 `etc`、`home`、`run`、`var`，没有 `usr` 或 `bin`。keep-id 下宿主读 upper 是 EACCES；`podman unshare` 里该文件显示为 uid 1，对应宿主 subuid，不是登录用户。upper 不能代替合并根，本轮也没有写它。

## 4. 从存储命名空间保存普通文件

第二段实验只写已停止容器的合并根，入口是 `podman unshare` 里的 `podman mount`。一条写入直接打开 merged 路径，另一条经 `chroot` 写入。写完后宿主进程仍是空目录或 EACCES。卸载并重新启动后，容器 root 读到了两个文件，原有的 `container-private` 还在。

| 模式 | 存储命名空间里的新文件属主 | 容器 root 再次启动后看到的属主 |
|---|---|---|
| 默认 rootless | uid 0 / gid 0 | uid 0 / gid 0，内容为 `from-namespace` 和 `from-chroot` |
| keep-id | uid 0 / gid 0（这里的 0 是存储命名空间里的宿主用户） | uid 1000 / gid 1000，内容相同，容器 root 能读 |

keep-id 的这次保存没有变成容器 root 的文件。它落在容器内 uid 1000 名下。容器 root 创建的旧文件仍是容器内 uid 0。两种身份会同时出现在同一棵根里。

## 5. 对 `/user/<发行版>/` 方案的约束

可见的完整环境目录如果只是把 merged 路径绑到 `/user/debian`，宿主文件管理器会看到空目录或权限错误，绝对链接还会在命名空间内指向宿主文件。

和本轮测量相容的分法是：

1. 用户文档和项目放在宿主进程能够直接读写的卷或绑定目录。停止环境不影响这些字节；本轮重启后容器能看到宿主写入。
2. 发行版根的浏览和保存走存储命名空间里的合并视图，并且在该视图的根上解析路径。绝对链接和容器内路径只有这样才一致。
3. keep-id 下要单独记录“宿主用户”和“容器 root”两个磁盘身份。用其中一个身份写入，不能当成另一个身份的文件。
4. 停止后的完整视图还要另外接上卷、私有 HOME 和其他持久挂载。只挂合并根会丢掉 `/var/ml-volume` 里的内容。

本机没有 id shifting。不能靠存储驱动把这些 uid 自动平移成宿主用户的同名文件。

## 6. 清理与未覆盖项

`podman ps -aq` 与 `podman volume ls -q` 在两段实验前后集合相同。结束时没有名字以 `ml-viewproto-` 或 `ml-viewsave-` 的容器或卷，`findmnt` 里也没有这些挂载残留。

还没有做：Fedora/Arch 镜像上的重复、Dolphin/KIO、跨应用保存、外部 `cp/mv` 后的归属恢复、合并根上的并发写、以及把命名空间视图做成常驻文件服务后的性能。挂载耗时只说明这次 Podman 命令的量级。
