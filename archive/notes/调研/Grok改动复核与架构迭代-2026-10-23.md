## 3. 本轮独立复核与补测

运行 `python3 -m unittest discover -s tests -v`：**156 项，152 通过、4 项集成测试跳过**。日志见[unittest.txt](../../evidence/architecture-review-2026-10-23/unittest.txt)。这验证当前离线回归，没有用跳过项冒充现场成功。

新增[文件归属与恢复原型](../../evidence/architecture-review-2026-10-23/probe.py)，在新建 Btrfs 临时目录和 `/dev/shm` tmpfs 中运行，不启停现有容器。13 项机制检查通过：

| 检查 | 观察及设计影响 |
|---|---|
| GNU cp 保留 xattr | 新副本仍带旧来源属性，但应采用目的根管理域；xattr 不是权威归属 |
| 无监听时外部 mv | 同文件系统 inode 不变，目的域已改变；当前域能按根恢复，历史来源没有日志就 UNKNOWN |
| 编辑器式临时文件替换 | inode 变化，所在项目及管理域不变；文件引用不能只绑定 inode |
| 两个管理根间硬链接 | 同一 inode 对应两个路径域；需识别别名冲突，不虚构唯一域 |
| 符号链接 | 按已解析目标核对域，不能只按链接所在目录授权；该 Python 探针不是抗竞态路径解析器 |
| Btrfs → tmpfs rename | EXDEV，源保留；跨盘移动不是单次原子 rename |
| 意图/暂存/目标发布后三处退出 | 独立子进程 `os._exit(77)`；每处恢复两次，均保留源，无重复登记 |
| 源被外部改写、目标占用、同内容无关目标 | 不覆盖或删除；即使目标哈希相同，也不能自动认成该事务的目标 |
| 清理 | 临时目录和子进程完成后无本轮数据残留 |

原始结果见[result.json](../../evidence/architecture-review-2026-10-23/result.json)。这是普通文件复制/发布与保守恢复实验：没有实现源删除；没有真实断电、inotify 溢出、ENOSPC、任意目录树或产品接入。tmpfs 的 fsync 也不构成掉电持久化证据。不能将“保留了源文件”写成“移动已完成”。

## 4. 复核发现的架构缺口

1. **目标契约与执行驱动尚未统一。** 合成的新 apt 目标能通过 `require_runnable`，实际 `driver_for` 却拒绝；合成 Debian 记录声明 dnf 时计划允许 dnf，实际执行按 target 使用 apt。正常 create 暂未生成这种矛盾，但迁移/扩展前必须统一验证入口。两项均在 result.json 留有可重跑观察；本轮未修生产代码。
2. **“检查版本后 rename”不能保证外部写入不丢失。** 直接共享和受管发布须分开标注保证；先查哈希不能消除后续窗口。跨盘源删除也有同类竞争。
3. **完整环境管理路径不等于透明 POSIX 根。** 卷覆盖、UID、停止状态都需要后端；服务端限制解析不自动解决宿主跟随 FUSE 绝对链接的问题。v2 明确原始链接元数据与管理投影的区别。
4. **每环境共享与每应用授权存在实际差别。** 同容器应用能访问挂载的共同范围；现有共享目录冻结，追加路径会触发更换。不能一边说“每次仅授予一个文件”，一边向所有程序暴露整个项目或 HOME。
5. **只读计划之后缺少替换编排。** 新旧环境实例、存活会话、文件视图和持久数据需独立身份/租约；名称复用不能继承旧授权，环境删除不能顺带删宿主项目。

已有源码的 `:z` 共享策略和 cwd 字符串前缀检查仍是待接入修正项；现有架构探针已记录其行为。本轮没有把它们描述为已验证的宿主越权利用，也没有把它们藏在新 UI 后面。

## 5. 本轮设计决定与下一步

v2 明确了环境 generation、独立数据根、按路径引用的文件、已验证执行上下文、文件视图租约、复制发布恢复状态、冲突处理，以及统一 target resolver 的职责。

建议下一次实现从 **统一契约入口 + 一个宿主项目调用 Arch 应用并正确保存** 开始；同时把停止环境只读投影当作独立技术关口。受管移动须先补源清理与故障矩阵，再开放“完成移动”的状态。先有这些闭环，再投入大规模管理 UI 和更多发行版。

直接共享项目保留性能优势，私有文件服务按需启动；不新增每进程发行版。性能预算继续标为规划值，没有因 13 项机制检查通过而上调成熟度。本轮更准确的状态是：**现有应用运行基础可继续使用；文件控制层的关键语义已进一步收敛，产品接入和日常文件完整性验收未完成。**
