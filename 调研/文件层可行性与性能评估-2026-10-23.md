# 文件层可行性、工程难度与性能需求评估

日期：2026-10-23，Asia/Shanghai。研究对象为[当前文件与执行架构](../设计/宿主权威与文件执行边界.md)，特别是第 18 节的完整环境路径、共享/独立文件、宿主管理及复制/移动归属规则。

结论：**核心逻辑可以实现，适合继续做原型；产品化难度高，主要风险在文件语义与故障恢复，而非分类查表的计算量。** 推荐“宿主政策服务 + 原生共享目录 + 按需环境私有文件视图 + 应用/项目执行上下文”。不要把所有磁盘访问都强制经过自有文件服务。

证据分为三类：本轮本机实验、读取核对的历史实验、官方机制资料。工期与资源预算另行标明，均不冒充实测。没有安装宿主包、修改生产代码、启动原有应用环境或改动宿主关联；本轮临时挂载与进程已清理。

## 1. 可实现到什么程度

| 目标 | 判断 | 实现条件与限制 |
|---|---|---|
| 每个环境有 `/user/debian/` 一类完整位置 | 可实现；中高难度 | 这是环境文件视图，内部仍用原生路径；要处理 rootless 身份、实际卷与停止状态 |
| 应用和依赖只在对应环境安装 | 已有基础；中等难度 | 保留原生包管理、环境 rootfs；用户快捷方式调用固定环境 |
| 注册菜单、打开方式和命令 | 已有基础；中等难度 | MIME 与命令入口可复用桌面机制；每种桌面/shell 仍有差异 |
| 共享/独立文件自动分类和路由 | 可实现；中等难度 | 分类应按文件角色、操作与已登记处理者生成；扩展名不能决定运行依赖 |
| 宿主调用 Arch CAD 编辑宿主项目 | 可实现，相关应用已有历史验收 | 文件位置和项目归属不变，应用进程在 Arch；旁文件、新建默认位置需补测 |
| 宿主普通工具管理容器私有文档 | 可实现；高难度 | 实际路径/FD 视图、正确的符号链接与 UID/GID 语义、保存和权限适配 |
| 原生 `cp/mv` 后更新管理关系 | 目录归属可可靠推导；历史来源仅部分可恢复 | 受管操作有事务，外部操作靠实际位置核对；不能承诺恢复所有历史动作 |
| 环境停止后仍浏览文件 | 可实现；中高难度 | 文件服务/存储视图单独保活，不要求整个桌面环境启动；不伪造 `/proc` 等运行期对象 |
| 任意应用不经适配自动走正确解释器 | 无法普遍保证 | 任意绝对路径执行、嵌入解释器、动态加载不会自动调用注册服务 |
| 任意 Linux 命令/驱动在任意宿主都原样成功 | 不能由共享内核方案保证 | 受宿主内核、架构、权限、设备和服务能力限制；必要时另设适配/虚拟机边界 |

后两项是范围限制，不是“多做几周文件管理器”即可消除的普通缺陷。目标中的“尽可能像原生”应通过逐类工作流扩展，而不以全量透明保证作为一期验收。

## 2. 当前逻辑必须补足的五个定义

### 2.1 管理归属不由编辑器决定

保留用户提出的归属规则：宿主 CAD 项目借用 Arch FreeCAD，仍由宿主管理；宿主编辑器打开 Arch 私有文件，原件仍属 Arch。默认以已登记的项目根/数据根确定归属，单文件例外少量记录。

同时保持四个不同字段：管理域、实际文件引用、用途、各操作处理者。Linux UID/GID 另行记录。打开/编辑不转移管理域；跨域复制产生新对象，移动成功后才转移。别名和共享挂载不生成新的数据归属。

### 2.2 “能打开”必须对应具体操作

标准 MIME 关联能说明哪个应用被声明用于某类型，以及默认打开者；它不保证无损编辑、执行、调试和格式版本兼容。我们的应用记录需要区分 `view/edit/run/convert`，并区分原生应用与环境应用。[MIME 关联规范](https://specifications.freedesktop.org/mime-apps/latest/)、[默认应用规则](https://specifications.freedesktop.org/mime-apps/latest/default.html)

例如 VS Code 能编辑 `.py`，不能据此移除其项目的 Debian Python 绑定；文本编辑器能读 `/etc` 配置，也不使配置脱离原环境。共享/独立是某次操作的处理分类，不是文件永久携带的单一发行版身份。

### 2.3 完整 rootfs 视图不是简单文件夹别名

当前宿主实查使用 rootless Podman 5.8.9 + overlay。Podman 官方说明 rootless 下非 VFS 存储的 `mount` 需要进入 `podman unshare` 用户命名空间；不能把 `podman mount` 返回的路径直接视作普通宿主应用稳定可用的产品接口。[Podman mount](https://docs.podman.io/en/latest/markdown/podman-mount.1.html)

不能直接编辑运行中 OverlayFS 的底层 upper/lower：内核文档明确该行为不受支持；多个活动 overlay 共用 upper/workdir 同样有未定义行为。需要受支持的 merged 视图或文件服务。[OverlayFS](https://docs.kernel.org/filesystems/overlayfs.html)

还有一个容易漏掉的根本问题：容器里的绝对符号链接 `link -> /usr/share/data`，从普通宿主 `/user/debian/link` 跟随时可能指向宿主 `/usr/share/data`。要提供正确访问语义，需由环境内文件服务解析、在视图中转换链接，或让访问进程进入目标 namespace。不能同时承诺“宿主直接跟随原样绝对链接”和“链接仍自动指向容器根”。维护界面可以显示原始链接文本，访问视图使用受控解析，二者标明差别。

因此这层可用性必须覆盖：真实卷、私有 HOME、UID/GID、ACL、xattrs、符号链接、停止/删除状态与挂载租约。它不是只暴露 `usr/` 和 `etc/` 名称。

### 2.4 外部操作只能做到可核对，不能恢复所有意图

inotify 不递归监视子目录，队列会溢出，处理时文件可能已经被重命名；健壮实现需检测丢失并重建相关缓存。fanotify 无特权模式也不能当成全盘拦截器：不能请求权限事件或标记整个 mount/filesystem。[inotify](https://man7.org/linux/man-pages/man7/inotify.7.html)、[fanotify_init](https://man7.org/linux/man-pages/man2/fanotify_init.2.html)

一个简单的不可辨识情形：用户在服务离线时复制 A 到 B 后删除 A，与独立创建内容相同的 B 后删除 A，最终状态可能相同。仅观察最终目录无法证明两者哪一种发生。完整复制还可能保留 xattr，使单文件标记被复制到两个对象。

实现政策应为：

- 数据根/项目根是当前管理域的依据；数据库保存例外、偏好和受管事务。
- 受管复制/移动写入恢复日志；原生外部操作按当前目录规则重新归类。
- 通知是加速缓存刷新的线索，启动、溢出及访问时进行核对；未知来源保留 UNKNOWN，不猜测。
- 不扫描整台机器、不为每次读取计算全文件哈希；按已登记范围、版本变化及风险决定是否校验。

这能维持正确的当前路由。要在所有外部工具、离线编辑和异构文件系统上完美保留历史来源，不符合“不侵入宿主”的约束。

### 2.5 文件迁移和数据库不能假装是一个原子事务

跨挂载 `rename` 可以返回 EXDEV，文件数据与注册表也不是同一事务域。SQLite 的事务只能直接保证数据库本身，不能替应用完成任意文件移动的原子提交。[rename](https://man7.org/linux/man-pages/man2/rename.2.html)、[SQLite 原子提交](https://www.sqlite.org/atomiccommit.html)

建议状态机：准备记录 → 目标暂存 → 校验/持久化 → 目标发布 → 登记新引用 → 删除源 → 完成。崩溃恢复要能区分“源仍在”“目标已存在”“数据库已更新但源未删”，遇到并发修改/冲突不覆盖。文件 `fsync` 不等于目录项持久化，发布/删除的目录需相应同步。[fsync](https://man7.org/linux/man-pages/man2/fsync.2.html)

跨文件系统不能承诺外部观察者在每一时刻都只看到唯一副本；可以承诺可恢复、无静默丢数据、状态可解释。

## 3. 建议采用的技术路线

| 路线 | 优点 | 代价 | 结论 |
|---|---|---|---|
| A. 保留 Podman；共享项目直接 bind；容器私有文件按需视图 | 延续已验收的原生包、生命周期和桌面代码；常用 I/O 不经过用户态代理 | 完整私有视图、身份及租约仍需开发 | **首选** |
| B. 把真实发行版根直接存成可见目录，重做运行时组织 | 宿主目录形态直观 | rootless 多 UID、快照、包更新、权限、绝对链接和恢复都要重做；普通目录本身不解决这些问题 | 不建议为路径外观重构现有运行时 |
| C. 所有宿主与环境文件统一经过自有 FUSE | 可集中提供一套虚拟命名空间 | 全部工作负载承担代理、缓存和一致性代价；故障影响面扩大；仍不能自动切换解释器 | 不作为默认数据路径 |

路线 A 下，宿主入口负责一次打开时的选择、授权、视图准备和进程启动。已获授权的源码/模型文件后续直接读写；只对需要的私有环境文档建立文件服务。自有界面和原文件管理器扩展复用同一后台，不在后台打开独立窗口作为依赖。

rootless 文件服务可以研究在运行时认可的用户/mount namespace 中访问目标 rootfs，通过私有通道提供文件操作，再投影给宿主。具体是否能完整支持停止环境、所有卷和身份映射是首个原型关口，不在本轮宣称已实现。

FUSE 的内核 passthrough 可减少部分 I/O 转发，但当前上游文档要求 `CAP_SYS_ADMIN`，并有内核配置/协商条件，不能直接写进无特权跨宿主方案作为免费加速能力。[FUSE passthrough](https://docs.kernel.org/filesystems/fuse/fuse-passthrough.html)

缓存也有语义代价。FUSE writeback-cache 假定修改经过 FUSE 内核路径；宿主或容器还可直接改底层文件时，必须设计失效机制，不能只开启缓存便承诺所有视图立即一致。[FUSE I/O modes](https://docs.kernel.org/filesystems/fuse/fuse-io.html)

## 4. 本轮文件访问实验

机器：Intel i5-1135G7（4 核/8 线程）、内核 7.2.11-200.fc44.x86_64、Btrfs；系统报告内存 7,794,960 KiB（约 7.43 GiB，通常标称 8 GB），实验前可用约 3.26 GiB。SSHFS 3.7.6、OpenSSH server 10.2p1、FUSE3 3.18.3。样本结束时记录的 memory PSI some avg10 最大 0.39%；日常使用主机，未锁频、没有清空页缓存。

全部文件位于新建临时目录。使用本机已装的 SSHFS 与 SFTP server，经 Unix socketpair 直接连接，**无网络、无 SSH 登录和加密**。这是可复现的“通用本地文件服务”代表实现，不是最终自有 FUSE、容器私有 rootfs 或性能上限。

四条路径：

1. native：宿主直接访问 Btrfs 目录。
2. bind：独立 user/mount namespace 中 bind 同一目录；未加入完整容器或 cgroup。
3. FUSE/SFTP cached：使用默认缓存的本地文件服务。
4. FUSE/SFTP strict：关闭目录/属性/entry 缓存并启用 direct_io；它只是更少缓存的测试配置，不表示已经证明全局强一致。

每条路径预热一次，再随机交错运行 7 波，共 28 个正式样本。每次核对全部小文件和大文件 SHA-256、20 次保存结果；测量不含 worker 启动、namespace 创建或挂载建立时间。

| 工作负载 | 原生 p50 | bind p50 | 文件服务 cached p50 | 文件服务 strict p50 |
|---|---:|---:|---:|---:|
| 2,000 个文件 stat | 33.1 ms | 34.9 ms | 71.2 ms | 486.5 ms |
| 逐个读取 2,000 × 4 KiB 文件并校验 | 56.9 ms | 59.2 ms | 353.6 ms | 960.4 ms |
| 顺序读取 128 MiB 并计算 SHA-256 | 206.1 ms | 205.0 ms | 367.8 ms | 378.1 ms |
| 20 次 4 KiB 写入、文件 fsync、rename、回读 | 71.8 ms | 74.2 ms | 91.9 ms | 105.5 ms |

中位数比值：bind 为原生的 0.99–1.05 倍；cached 小文件读取约 6.21 倍，strict 约 16.87 倍；顺序读取分别约 1.78、1.83 倍。**这些倍数只描述本轮程序、参数和主机，不能写成“FUSE 一定慢 6 倍”或“所有容器开销不超过 5%”。**

解释与限制：

- 原生和 bind 相近，支持保留普通共享目录的直接数据路径；不能由此得出所有完整容器/磁盘性能结论。
- 用户态往返对小文件更敏感。新依赖安装、源码扫描、IDE 索引若全部经过通用文件服务，可能明显影响体验。
- 顺序读取包括 Python 循环和 SHA-256，且底层页缓存已预热；它不是磁盘冷读取带宽。
- 保存实验只同步文件，没有同步目标目录，不证明断电恢复能力。
- 两条文件服务都在一次宿主替换后立即读到新内容；单次结果不能证明 mmap、监听、长期缓存和所有竞态正确。
- 7 波只报告 p50 和范围，不把小样本 p95 当作可靠尾延迟 SLO。

原始证据：[result.json](../evidence/file-layer-feasibility-2026-10-23/result.json)、[汇总](../evidence/file-layer-feasibility-2026-10-23/summary.json)、[验证](../evidence/file-layer-feasibility-2026-10-23/validation.json)、[可重跑脚本](../evidence/file-layer-feasibility-2026-10-23/probe.py)。验证仅证明实验输出和清理一致，不是新文件层产品验收。

### 注册表成本

另用 SQLite 创建 100,000 条合成记录，字段为路径、管理域、角色、处理者，加路径主键。数据库约 **8.84 MiB**。预热后 5,000 次随机索引查询 p50 **85.3 ms**，摊销约 **17.1 微秒/次**，7 波全部核对返回值。

这是本地缓存命中的数据库查询，**不包含 IPC、路径安全解析、MIME 检测、授权、进程启动和磁盘扫描**。它说明“归属和处理者查表”不必成为主要性能瓶颈；不意味着一次实际路由只需 17 微秒。100 万条记录若保持完全相同的窄 schema，大致是百 MiB 级磁盘量，实际索引、权限、历史及长路径会增加空间，不能把线性外推当实测。

### 内存与测量缺口

两个 SSHFS 客户端最终 PSS 分别约 2.57、5.90 MiB；Python workload worker 约 13.7–13.8 MiB。但两个 SFTP server 的 `smaps_rollup` 返回 Permission denied，**本轮没有取得整条文件服务的完整 PSS**。这些进程数据也不含内核 FUSE、文件页缓存或未来产品 broker/UI。保留错误，不填零、不求一个不完整的“总内存”。

## 5. 既有证据能支持哪些预估

以下为本轮读取核对的历史结果，没有重跑 GUI：

- 修复后 Debian/Arch Mousepad 冷启动 p50 分别约 **884 / 887 ms**，p95 约 **1.03 / 1.07 s**，每环境 10 次；最后关窗到容器 died 约 **199 ms**。[生命周期报告](../evidence/lifecycle-2026-10-22T213032+0800/report.md)
- 早一轮三环境 Mousepad 热启动 p50 为 **0.586–0.672 s**，每环境 30 次；该轮随后暴露过生命周期缺陷，所以只作为旧启动路径参考，不当作新文件层或当前全产品结论。[旧启动报告](../evidence/startup-2026-10-22T182400+0800/report.md)
- 并发场景中，一个 Debian 环境的 1–4 个 Mousepad 窗口，其 cgroup memory.current 中位数约 **24.1 / 46.7 / 69.9 / 94.8 MiB**；每规模只有 3 波。这是特定轻应用场景，不代表 FreeCAD、浏览器或编辑器的内存。[并发报告](../evidence/concurrency-2026-10-22T220318+0800/report.md)

并发报告有一处统计展示需注意：S6 比较表列出的是 p50，而“倍数”来自 **mean/mean**。例如 current 的 p50 是 69.9 与 71.1 MiB，但 1.195x 来自 74,648,234.667 与 89,229,994.667 字节的均值比。此处核对了 `summary.json` 和 `tools/probe_concurrency.py:2085` 附近实现，不把倍数误写成 p50 比。不在本轮改写历史报告。

旧并发 PSS 采集循环会忽略部分 `/proc/.../smaps_rollup` 读取错误，当前不能把那些约 1–3 MiB 值直接视为所有应用进程的完整 PSS。本文采用 cgroup 数据描述该场景，并把完整 PID 覆盖度核对列入后续测量要求。

基础镜像当前 `podman image inspect .Size`：Debian **155.0 MiB**、Fedora **364.4 MiB**、Arch **391.4 MiB**，三项简单合计约 **910.8 MiB**。这是镜像报告大小，不是安装完整应用后的空间，也不是去重后 `du` 的独占磁盘占用。[本轮镜像记录](../evidence/file-layer-feasibility-2026-10-23/base-images.json)

## 6. 预期性能与资源预算

本节数值为**工程规划预算/验收目标，尚未由完整产品验证**。假设单用户、三环境、约 10–100 个已登记项目、10 万级文件索引、本地 SSD，采用路线 A，无全盘扫描，不把数据库或编译树放到通用 FUSE 慢路径。

| 项目 | 规划范围或目标 | 依据与边界 |
|---|---|---|
| 后台路由/注册服务 | PSS 32–128 MiB 预算 | 覆盖 Python/编译型服务、SQLite 连接与有限缓存的设计余量；未测产品 |
| 每个活动环境文件服务 | PSS 10–50 MiB 预算 | 多进程、协议缓存及实现差异；本轮只测到客户端，完整总量未知 |
| 自有管理窗口 | 打开时增量 PSS 100–300 MiB 预算 | 原生 Qt/GTK 轻界面设定；共享库分摊、缩略图与实现影响很大；未做 UI |
| 三环境文件服务全部活动、管理窗口关闭 | 新增用户态 PSS 约 62–278 MiB 的预算合计 | 32–128 + 3×10–50；不含应用、已有运行时、页缓存和内核内存 |
| 后台空闲 CPU | 目标低于单逻辑核 1%，大部分时间等待事件 | 以无文件变动、无 UI、无初始化扫描为条件；不能保证持续构建时也如此 |
| 缓存命中的路由处理 | 额外 p95 ≤20 ms 的目标 | 不含应用启动、环境唤醒、首次挂载与交互授权；需实际 IPC/权限实现验证 |
| 普通共享项目 I/O | 对代表任务争取 ≤5–10% 增量 | 设计验收目标；本轮 bind 样本支持研究此目标，不是普适性能保证 |
| 容器私有文件视图 | 暂不承诺固定百分比 | 明确测小文件、原子保存、并发及缓存失效后再设 SLO |

因此没有理由一开始就为控制层准备几个 GiB 内存；但也不能把整个产品说成只有几个 MiB。**主要内存仍取决于实际应用和页面缓存，新增文件层的规模取决于是否扫描/缓存过量内容。**

应用启动不能简单把“0.9 s + 20 ms”当完成后的保证，因为新视图准备和租约可能在关键路径上。首次访问私有环境还可能增加文件服务和挂载建立成本，本轮未测；已有环境中连续短命令应复用会话，避免每条命令重复若干次 Podman inspect。

### 硬件与空间规划

| 使用场景 | 建议规划 | 当前证据边界 |
|---|---|---|
| 轻量命令、文档编辑和开发验证 | 现有 4 核/8 线程、标称 8 GB 内存可继续做原型 | 本机已完成轻 GUI 和此次实验；不等于全产品最低配置认证 |
| 日常 IDE + 浏览器 + 多环境工具 | 按 16 GB 内存规划更有余量 | 工程容量建议，需按用户实际应用复测 |
| 大 CAD 模型、多个重应用、并行构建 | 按 32 GB 或应用自身需求规划 | 应用需求主导，不把它归咎于容器文件层 |
| 三环境及常见开发/GUI 包，保留一轮恢复空间 | 可先预留 30–60 GB 可用空间，不含用户项目 | 是容量预留，不是测得的安装大小；应用清单、缓存及快照策略决定最终值 |

同一发行版多个应用尽量共用环境和不可变基底；跨发行版库不按名字强行去重。reflink/镜像层可减少部分磁盘副本，不等于所有进程共享同一内存页。

跨域复制 S 字节文件，目标通常至少需要额外 S 字节容量，源在验证完成前仍保留；备份、暂存和恢复点可能进一步增加峰值。不要为实现归属标签而复制原本已能直接共享的项目。

## 7. 实现难度与工期估计

假设：以现有代码为基础，一名熟悉 Linux namespace、文件系统、桌面集成及测试的全职工程师；有 AI 辅助，但把实机验证、崩溃恢复和兼容调试计入。**以下是工程判断，置信度有限，不是交付承诺，也不能从代码行数推导。** 不含 ARM/x86 翻译、内核驱动兼容、完整 VM 后端或所有第三方应用适配。

| 工作包 | 难度 | 单宿主日常可用版估计 |
|---|---|---:|
| 数据域、应用能力、路由规则与迁移 schema | 中 | 2–3 人周 |
| 完整环境文件视图、身份、链接与存储租约 | 高 | 3–5 人周 |
| 应用导出、项目会话、首个桌面接入 | 中高 | 2–4 人周 |
| 保存/复制/移动、冲突和事务恢复 | 高 | 2–4 人周 |
| 外部变化核对、失效与停止/删除处理 | 高 | 2–4 人周 |
| 自有轻管理界面 | 中 | 1–3 人周 |
| 数据完整性、故障注入、性能和回归验收 | 高 | 4–5 人周 |
| **累计** | **高** | **16–28 人周** |

阶段可以这样理解，均为累计工作量：

- **演示闭环：2–4 人周。** 固定共享目录、已登记应用、基本项目终端；不含完整 rootfs 双向管理和可靠外部移动。
- **受限 MVP：6–10 人周。** 单 Fedora/KDE 宿主、三种客体、普通文档视图、受管复制/移动及基本恢复，明确不支持的文件操作。
- **单宿主日常可用版：16–28 人周，约 4–7 人月。** 达到上表范围，补保存语义、可靠核对和异常恢复。
- **三类宿主 + KDE/GNOME 等桌面广泛适配：累计约 36–60 人周，约 9–15 人月。** 仍不等于任意发行版、任意内核/应用全兼容。

两名工程师可并行处理核心与桌面，但存储契约、集成和实机验收在关键路径上，日历时间不宜直接除以二。若要求首版同时做到“完整可写系统树、所有 GUI 文件选择器、所有 shell、跨盘事务和每应用强隔离”，应重新扩大估计。

## 8. 优先原型与继续条件

先做三个验证原型，避免先投入大型文件浏览 UI：

1. **完整环境视图原型**：在新建环境中验证宿主浏览、绝对/相对链接、普通文档保存、UID/GID、独立卷、停止状态读取及干净撤销。不能改宿主源目录标签来掩盖权限问题。
2. **跨应用保存原型**：宿主项目 → Arch FreeCAD/文本编辑器 → 原文件保存；覆盖相邻资源、临时文件 rename、新建默认位置，以及另一进程同时改源文件时的行为。
3. **归属与恢复原型**：通过自己的服务及外部 `cp/mv` 操作，模拟进程退出、通知丢失、跨挂载失败与重启。能够恢复当前管理域；无法证明历史来源时明确 UNKNOWN。

继续条件：没有静默数据丢失；运行环境明确；宿主和容器文件引用不混淆；普通共享项目不被迫走慢文件服务；背景空闲占用可控；所有不支持情况可见。完成这些后，再投入菜单细节、管理界面与跨桌面适配。

性能下一轮至少增加：真实容器内文件服务、冷/热挂载耗时、3 环境并发、大目录遍历、Git/语言包安装/IDE 索引、文件锁与 SQLite、mmap/inotify、外部替换缓存失效、完整进程树内存及 cgroup、服务崩溃。当前 28 波机制实验不能代替这些验收。

## 10. 同日后续：环境视图原型

第 8 节第 1 项已在锁定的 Debian 13 镜像上做了一轮实测，细节见[环境文件视图原型](环境文件视图原型-2026-10-23.md)。测量改变了这一项的实现前提：rootless 下宿主进程不能直接浏览 `podman mount` 的合并根；绝对链接要在该根上解析；独立卷的字节在卷目录。通过 `podman unshare` 写入已停止合并根的普通文件，容器重启后能读回。keep-id 下这次写入的容器内属主是 uid 1000。写完第 10 节时，第 2、3 项还没做；第 2 项见第 11 节。

## 11. 同日后续：跨应用保存

第 8 节第 2 项已在保留的 Arch FreeCAD 环境上做了一轮实测，细节见[跨应用保存原型](跨应用保存原型-2026-10-23.md)。共享项目里的 FreeCAD 保存和同目录 rename 会写回原路径，第二次保存留下同目录备份，旁边的 STEP 不跟随更新。没有文件名的保存不会落盘；相对路径和家目录跟随容器进程。排好顺序的交错表明，后到的 rename 盖掉宿主刚写入的新文件，写到旧描述符则不会。第 3 项归属恢复还没做。
