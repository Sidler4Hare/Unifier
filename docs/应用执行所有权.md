# 应用执行所有权与租约恢复

2026-11-05 工作树实现，随后进入 v0.0.4 发布包和日常入口。此文描述受管 APP 路径，不改变普通 `env exec` 或项目会话的执行语义。目标发行版里的 subreaper、pidfd 和真实 Podman 生命周期仍未验收。实机及 GUI 仍受 [测试规范](测试禁令与规范.md) 约束。

## 受管执行

`--on-demand` 的 open/exec 使用已有 FD 3 身份握手，客体自己的 Python3 运行一个 Linux subreaper。它启动应用并等待全部已收养后代，包括双重 fork、`setsid` 后的后台进程。只有 `waitpid` 确认无剩余子进程后，才写入 token 对应的终态回执。监督者消失、宿主 Podman 代理退出或 probe 失败都不能证明应用已结束。

客体需有 Python3、subreaper 和 Python 的 pidfd 控制接口；缺少能力时明确拒绝，不自动安装解释器、不复制宿主二进制或切回无法监督的启动方式。应用沿用登记的用户、环境变量、argv 和工作目录。

租约 schema 3 保存环境 UUID/generation、完整 CID、执行 token、客体监督者 PID/starttime，以及 `not-started → starting → running → exited` 状态。不能确认启动/终止时保留 `recovery-required` 和租约。只有明确的启动前拒绝或可核验的终态允许释放。客体回执位于该用户私有的 `/tmp/.unifier-app-<uid>/`，宿主状态位于管理根 `.lab/leases/<env>.json`。

前台退出码在监督后代结束后返回；后台启动器先退出时，worker 继续等待。后台执行若脱离子进程树、通过另一个常驻服务代启，当前协议不能证明该执行的归属。

## 共享和单实例边界

多个 APP 和项目会话共用同一租约集合。短激活请求结束只释放它自己的执行租约；已有受管实例的租约和 bridge 继续保留。最后一个可验证执行结束后，仅当完整 CID 与启动时间仍属于本组，才自动停止环境。手动预启动或重启的环境保留。

**通用单实例协议映射仍未实现。** 短请求的进程树退出不证明一个外部实例结束；本版本不会把旧 lease 转移到本次短请求，也不能为未受管外部实例建立生命周期证明。使用 D-Bus 等服务代启、依赖外部单实例的应用，应使用手动预启动的环境；不得将本次微型进程测试当成这类应用的自动生命周期验收。WPS 的具体行为仍需真实保存/关闭/重开验证。

## 查询、恢复与取消

以下命令中的环境 ID 和 token 来自当前管理根的实际记录：

```bash
unifier app leases <environment>
unifier app recover <environment>
unifier app recover <environment> --token <token>
unifier app cancel <environment> <token>
```

- `leases` 输出共享状态，不启动容器。
- `recover` 保留活跃 worker。worker 已退出时，查询同一个已运行 CID 内的 token 回执；只有完整终态或确切 CID 已停止才允许收尾。未知返回 `kept-unknown` 和非零退出码，不启动停止态容器取证。
- `cancel` 只向经过 token/PID/starttime 校验的监督者发送 TERM。监督者用 pidfd 向属于该执行的后代转发信号，10 秒后仍有残留才定向升级 KILL；未知则保留租约。不会按进程名或对整个共享容器发信号。
- 取消时若原 worker 仍存活，返回 `lease=awaiting-worker`，将终态留给 worker 读取退出码并释放，避免二者争抢收尾。worker 已退出则返回 `lease=released`；期间 worker 崩溃可再 `recover`。

旧 APP lease 缺客体身份时保留为 unknown，不因宿主 PID 失效自动删除；项目 lease 继续走项目恢复入口。损坏 JSON、未知 schema 或代际/CID 变化明确拒绝，不将损坏状态当成空租约。不要删除 lease/回执文件强行解锁；旧版忽略新状态，活跃执行或未恢复租约存在时不能直接降级。

## 当前验证范围

`tests/test_application_supervisor.py`、`tests/test_application_lifecycle.py` 使用受保护的宿主微型进程和 fake 容器边界，覆盖 daemonize、双重 fork/setsid、精确取消、终态丢失、worker 恢复、共享租约及真实 FD 3 通道。它们是 T1 本地内核机制证据；目标发行版中的执行、真实 Podman 生命周期、私有 GUI 和账号/媒体工作流均未由这些测试验收。
