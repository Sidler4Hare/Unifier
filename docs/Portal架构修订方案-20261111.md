# Portal 与宿主文件访问架构修订方案

审查基线：`f35ffe99`（13 个生产模块及其测试/文档），对照现有 FileRef/static mounts、desktop/on_demand 生命周期及尚未接入的 HostShareView。日常 r6 的单次钉钉上传已成功；这里是设计审查与实施方案，不宣称下列修订已经实现或部署。既有缺陷与验收边界见 `Portal文件交付-设计与验收.md`。

## 结论

保留现有 xdg-dbus-proxy 过滤层、客体动态库校验、openat2 固定源对象、有界快照和租约机制。应围绕「访问授权对象」重组边界，而不是继续往 D-Bus Client 或启动器中堆文件系统和恢复逻辑。启动兼容、协议传输、用户授权、交付介质、消费者生命周期是不同职责，不能互相代替。

当前最大结构问题是同一资源经过不同入口便获得不同语义：FileRef 路由要求静态共享；kdialog/zenity 自己翻译路径；原生 GTK/Qt 在 Response 中复制文件；HostShareView 有对象/FD 规则但未接入入口。路径转换分散，取消和清理没有共同事务，发布版与工作树又不一致，最终表现为“探测成功、窗口正常，应用读不到”。

## 建议的模块边界

| 层 | 唯一职责 | 不应承担 |
| --- | --- | --- |
| CompatibilityResolver | 按 ABI/工具包实际能力选择 native/GTK Native/命令适配，输出可审计理由 | 文件授权、按应用版本硬编码二进制修补 |
| PortalTransport | 过滤代理前的连接、序号/FD/唯一名传输、协议帧预算 | 复制文件、同步阻塞式 owner 查询、租约目录清理 |
| SelectionCoordinator | 请求状态机，验证响应来源与请求代际，异步提交授权/交付，发送唯一终态 | 自行决定宿主根目录策略 |
| AccessBroker | 统一授权主体、对象身份、用途与权限，生成 grant，决定允许的交付后端 | 从 URI 文本推导已获授权，假定所有入口规则相同 |
| DeliveryBackend | StaticMapping、ReadOnlySnapshot；将来再接 ControlledView/DocumentExport | 自行提升权限或把快照冒充可写原件 |
| GrantJournal / LeaseManager | 持久归属、代际、恢复、幂等撤销与配额账本 | 依赖日志解析来判断 ready 或所有权 |
| Diagnostics | 稳定原因码、可关联事件、版本与能力矩阵、日志保留 | 保存文件正文或将 IN_ACCESS 等同上传成功 |

不必为此新增全局常驻服务或 root 守护进程。可继续使用按环境、随应用租约存活的宿主进程；先把协议与纯状态机/存储模块拆开，使用接口替换，保持现有部署方式。

## 授权对象与信任边界

建议最小 `AccessGrant`：grant_id、环境 UUID/generation、应用/执行租约身份、已核验的请求来源、源对象 dev/inode/mount 身份、用途（上传/读取/编辑/目录）、权限、交付后端、客体 URI、创建时刻、状态、消费引用与错误码。路径是定位与显示字段，不是权限凭据；对象发生替换要明确拒绝或重新授权。

主体必须由可信启动/连接归属确定，不能相信客体提交的 app_id。当前同 UID、同桥接挂载意味着环境级共享，不能仅加一个 app_id 字段就声称实现应用隔离。需要真正的应用级隔离时，必须另设计 UID、挂载命名空间或受控访问代理的强制边界；默认明确告知现有环境级语义。

所有入口调用同一个授权服务，但保留不同用途。统一策略组合顺序：环境身份 → 主体及用途 → 用户选择证据 → 管理员限制/黑名单 → 实际对象和挂载核验 → 后端能力。当前 SelectionStore 以选中文件父目录临时构造 HostSharePolicy，只复用路径检查，不能当作完整全局策略生效。

## 请求与交付事务

状态机：NEW → WAITING_PORTAL → AUTHORIZED → MATERIALIZING → DELIVERED → RELEASED；任意未交付阶段可进入 CANCELLED/FAILED/EXPIRED。终态只产生一次；所有异步回调携带 request_generation，旧代际/重复回调不得发布 URI。

1. 建立请求与 owner 身份；owner 变化使原请求失效，不把新 owner 接续到旧授权。
2. 成功响应只允许创建待提交 grant。复制在独立串行 worker 执行，主事件循环不阻塞。
3. 先固定源 FD、预留容量、写私有临时文件、核验对象与字节数，再原子发布。发布前复查取消状态。
4. 取消、超时、断线走同一终止接口；通知客体终态，并有界关闭宿主请求。不能像当前 expire() 一样仅删除关联后丢弃晚到响应。
5. 记录交付失败与响应发送失败的不同阶段。当前 selection-delivered 写在 send() 前，不能单靠该事件证明消费者收到了 URI；新事件应区分 prepared、response-queued、read-observed、user-confirmed。
6. 无可靠消费完成协议时保留租约级生命周期；不能把读到一次或任意 TTL 当作上传完成。未来显式 acquire/release 支持提前回收，旧客户端继续保持安全的租约回退行为。

## 生命周期与容量

- 使用专用 ready 控制通道/版本化握手，含 protocol_version、capabilities、PID/starttime、generation。当前 start_bridge 通过审计文件字符串识别 ready，并重复解析日志；日志不能承担控制协议职责。
- GrantJournal 放在客体不可写的位置。创建、交付、撤销、回收记录必须绑定目录 inode 和环境代际。异常重建先处理旧 manifest，再发布新记录；当前“bus 活着、delivery 已死”分支遗漏旧快照清理的问题优先修。
- 恢复失败保留隔离状态和明确原因，不能覆盖旧记录后失去归属。停止过程即使某次 close/rmtree 失败，也应继续关闭其他自有资源，并记录未清理项。
- 配额统一预留/提交/释放：磁盘字节、对象数、排队字节、FD、并发复制。静态映射不应消耗复制批次，取消应回退预留。现有每连接 256 条、单条 16 MiB 限制不能替代全桥接排队字节上限；溢出只安排一次关闭。
- 配额耗尽给稳定原因码与释放路径，不静默降级。日志要轮转并标记截断；当前 1 MiB 后不再写入会让用户失去诊断依据。

## 会话与版本

将 session_generation 与 container_generation 分开。启动前比较实际 Wayland/X11/Portal 资源与容器挂载；不匹配就交付具体迁移方案，不能长期依赖 wayland-0 → wayland-1 临时链接。刷新不能打断同环境其他租约。

发布使用源码清单摘要、能力 schema 版本和构建来源；doctor 展示安装入口、运行 bridge、应用模式、会话绑定及 grant 状态。兼容探测必须针对实际选中的入口，不能以 CEF Portal 探测成功代替 GTK 自定义入口。新增模式或能力版本通过明确定义的迁移处理，不能自动复用旧进程后假定新代码已生效。

## 实施顺序与验收门槛

1. **行为修补小步提交**：超时唯一终态、异常重建回收、全局排队字节预算；先用 fake clock、私有总线与低配额 fixture 复现，不动用户桌面。
2. **抽出状态机**：纯 RequestState + fake transport；覆盖 owner 切换、Close/成功竞态、发送失败、重复 token、超时迟到；保持当前 r6 上传语义。
3. **持久化授权/配额账本**：故障注入覆盖创建前后、复制中、发布前后和清理失败；恢复只触及已核验对象；验证旧租约可读、新写入版本化。
4. **统一入口**：先让原生 Portal 与命令助手使用同一只读授权接口，再适配 FileRef 路由。用相同契约用例验证多选、Unicode、链接、嵌套/遮蔽挂载、只读权限、目录和写入拒绝。
5. **可写/目录另行设计**：选择 ControlledView 或 DocumentExport 前先做能力与隔离评估；必须验证编辑、保存、关闭、重开、源替换和冲突，不用快照同步伪装原件写入。
6. **发布与实机矩阵**：不可变候选检查通过后再逐个 GTK、Qt、命令助手人工验收；冷启动、取消、读取/上传分别记录。不要把钉钉一个成功样本外推为全平台兼容。

## 仓库与测试资产架构

`src/tests/tools/fixtures` 保存现行实现和可再生最小回归；验收报告只保留精简、脱敏的契约和结果。原始日志/截图/解包树/历史源码副本属于外部运行存储，带 run_id、保留时间和空间配额。运行器按“工作负载+fixture+证据”计总预算，大 Git 快照放磁盘而非默认内存盘。

本轮清除旧 archive/evidence 与过时原始产物并保留 Git 历史恢复路径，现行 tests 不按年龄删除。未来新增回归必须绑定现行契约或已修缺陷；历史桌面自动化探针不默认执行。历史报告中的证据链接保留历史含义，恢复旧材料后才能复跑。
