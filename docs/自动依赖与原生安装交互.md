# 自动补充运行库与原生安装提示

`unifier install` 和 `unifier pkg install` 安装成功后默认检查目标软件包中的 ELF 文件，包括插件 `.so`，通过客体自己的仓库查找并补装未声明的运行库。发行版声明的普通依赖仍由 apt、dnf、pacman 处理。

```bash
unifier install --target debian13 ./feishu.deb
unifier pkg install debian13 --file ./feishu.deb

# 已安装的软件也可以重新检查，无需重新下载厂商安装包。
unifier pkg repair-deps debian13 bytedance-feishu-stable

# 程序在运行时拼接库名，静态检查无法发现时，可提供错误中的精确 SONAME。
# 仍由产品查仓库和安装，无需人工找包下载。
unifier pkg repair-deps debian13 --library libasound.so.2
```

命令中的环境 ID 要替换为当前安装根中的实际 ID；原有日常环境不自动迁移。`UNIFIER_HOME` 继续决定记录与事务目录。

## 原生交互

stdin/stdout 都是终端时，默认显示包管理器原生进度、下载大小、确认及选择提示，并传递输入和窗口尺寸。不强加 `-y` / `--noconfirm`。Debian 使用 `readline` 配置前端；提示沿用包事务的 `C.UTF-8` 语言环境。

v0.0.2 的交互 apt-get 关闭其内层 dpkg PTY，以继续传递终端缩放；确认和维护脚本输入仍保留，APT 内层进度样式随之改变。中断后的清理、未知状态和 `pkg recover` 见 [v0.0.2](v0.0.2.md)。

- `--interactive`：明确要求真实终端；没有终端时在操作前报错。
- `-y` / `--yes`：使用原生非交互选项，仍显示实时原生输出。
- `--json`：非交互并仅输出 JSON 结果，不混入原生进度；与 `--interactive` 互斥。
- `--no-repair-deps`：安装时跳过额外 ELF 检查，原生包管理器的声明依赖解析仍然执行。

`pkg update`、`pkg remove` 同样支持原生交互模式。无终端的脚本默认非交互；本版不会在后台等待不可见的原生确认。

## 检查及记录

检查器用 `readelf` 读取数据，不通过 `ldd` 或启动厂商二进制来探测，不以 root 运行应用。缺少扫描工具时在客体安装 `binutils`。Debian 按需安装 `apt-file` 并更新 Contents 索引；Arch 使用 `pacman -Fy` 文件索引；Fedora 使用 DNF repoquery 的 64 位 SONAME 提供者查询。

只从目标容器配置的仓库选择运行库，不下载来历不明的 `.so`，不改宿主包数据库，不关闭签名验证。候选唯一才补装；候选缺失、歧义、网络错误或补装后库仍缺失都会留下失败结果。Arch 的安装保持完整 `-Syu`，不用局部升级替代。

安装与补装共用环境包操作锁、宿主/其他环境隔离检查和包清单更新。事务的 `dependency_repair` 保存扫描范围、ELF 数量、缺失库、候选、选中包和重新检查结果。原生命令的参数、退出码及输出尾部保留在 `native`；终端模式的 stdout/stderr 合并为终端记录。

2026-11-05 工作树增加管理根级包事务协调：安装、升级、卸载、补库、恢复及环境集合变更先排队，再取环境锁；一次包事务从前置观察到最终记录持久化保持同一窗口。默认排队最多 30 秒，取消、繁忙和超时明确报错，等待期间不启动容器或写包数据库。应用启停保持独立。未部署的工作树行为与 v0.0.2 安装版分别核验；同伴只读清单的支持范围见 [接口说明](包清单只读观测.md)。

为保留既有 Python 服务调用契约，直接调用 `EnvironmentService.install_*` 时须传入 `repair_dependencies=True`；两个安装 CLI 默认传入该选项。

## 能力边界

这是 x86_64 ELF 的 DT_NEEDED 静态检查和补装，不是任意程序运行错误的自动修复。纯运行时构造的 `dlopen` 名称、脚本解释器/模块、安装脚本漏声明的外部命令、ABI 符号版本、Qt 后端、账号和媒体功能不由本检查器推断。

软件包自带的同名库记录为 `bundled_candidates`，不据此证明实际 RPATH、wrapper 的环境配置或运行时加载正确。发现未支持 ELF 架构会明确拒绝。安装成功与补齐运行库也不等于 GUI 工作流通过。

2026-11-05 工作树将有 bundled 候选的结果明确设为 `status=bundled-candidates-unverified`；CLI stderr 和交互安装结果提示加载尚未验证。原生包事务仍可 `phase=completed`，其退出码表示包事务结果。旧 JSON 字段保留，新增 `elf_objects`、`dependency_edges`、`static_resolution`、`evidence_scope`；每对象记录架构、词法 ORIGIN、RPATH/RUNPATH 及名称候选。静态路径记录不模拟动态加载器，`runtime_loading`、`workflow`、符号版本、RUNPATH 传递性、wrapper 环境和 `dlopen` 保持 unverified。

显式诊断 API `loader_verification.verify_fixture_loading()` 只接受可信微型 fixture、至多 16 个文件/合计 4 MiB 的 SHA-256 清单、私有目录、普通客体 UID，以及已运行的精确环境绑定。它不启动容器，不自动作用于厂商 ELF。使用目标系统加载器的 `--list`，以空白私有环境解析初始依赖图；记录原生退出码、输出摘要和范围。完成帧、退出码和诊断共同判定：缺少符号版本即使退出码为 0 也为 verified-fail；其他无法解释的诊断为 unverified。不得将一次初始图 verified-pass 解读为已执行程序、完成全部符号重定位、验证插件 `dlopen` 或工作流。

本机 C/ELF 微型 fixture 已验证这些区分；此证据属于 T1，不能替代 Debian/Arch 目标加载器的 T2 验收。该 API 不是自动补库成功的附加证明，也未向日常安装版部署。
