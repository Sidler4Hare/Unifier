## 减少手工定位缺库

已有 ELF 扫描仍默认在正式安装入口运行。运行时 `dlopen` 等错误未进入静态扫描时，可以直接使用保存的错误日志，无需人或 AI 逐条抄写 SONAME、查包或下载 `.so`：

```bash
# 只在本地解析日志，不访问环境、不启动容器、不安装包。
unifier pkg repair-deps 实际环境ID --from-log ./runtime.log --diagnose-only --json

# 对明确的缺库错误，交给正式包事务查客体仓库、安装唯一提供者并复查。
unifier pkg repair-deps 实际环境ID --from-log ./runtime.log --json

# 也可同时复查原应用的软件包。
unifier pkg repair-deps 实际环境ID 实际包名 --from-log ./runtime.log
```

识别的是 loader/dlopen 明确报告的 `libname.so.N: cannot open shared object file: No such file or directory`。日志里的任意 `.so` 字符串、绝对路径、符号版本或权限报错不会被猜成可安装依赖。ABI/符号、权限、外部命令和未定位的插件问题分类输出；混合出现这些问题时，自动补库在访问环境前拒绝，避免安装后误报整体修复成功。

日志必须由调用方明确选择，适用于当前环境和应用版本；旧日志不能证明当前缺库。输入至多 1 MiB、32 个唯一库，拒绝非普通文件、最终路径符号链接、二进制/非法 UTF-8、读取中变化和超限输入。事务只保存结构化类别、库名和输入哈希/大小，不保存原文和日志路径。普通原生命令输出仍按原事务规则记录，提交日志前自行去除其中的凭据。

执行补库沿用原生包管理器、管理根协调、环境锁、恢复门槛及同伴隔离检查。唯一提供者才安装；歧义、查询失败、安装无效、未知状态和递归上限仍明确失败，不自动切换仓库、放宽签名或重跑应用。包事务完成后 `runtime_loading` 与 `workflow` 仍为 `unverified`，需要实际加载和工作流证据。完整约束见 [依赖说明](自动依赖与原生安装交互.md)。

诊断输出的 `library_repair_candidate` 仅表示可进入查库阶段，`provider_resolution=not-run` 明示本地诊断没有查询提供者。后续减少手工收集日志、处理加载路径及恢复编排的顺序见 [依赖自动化迭代](依赖自动化迭代.md)。

## 汇总的控制层改动

| 范围 | 本版内容 | 尚未完成 |
|---|---|---|
| 包事务 | 管理根 flock 覆盖前后观察与最终持久化 | 同管理根真实多环境验收 |
| 同伴清单 | 停止态 Debian 数据库有界读取与存储引用日志 | 真实等价性/释放验收、运行态与 Arch/RPM 适配、模糊引用恢复 |
| 应用生命周期 | subreaper 监督后代，APP lease 查询/恢复/精确取消 | 目标客体/GUI、通用单实例和服务代启 |
| 依赖结果 | bundled 候选与加载/工作流证据分层；日志提取缺库提示 | ABI/插件/桌面服务的通用自动修复 |
| 受控请求 | 宿主签发的 host-info/project-run 原型 | broker 专用信号收尾、请求日志自动恢复、原生 Agent 全工作流 |

11 月 5 日组装过程见 [v0.0.3 组装报告](../artifacts/release-v0.0.3-20261105T152926+0800/report.md)。2026-11-07 已用当前树重新打包并切换日常入口；该切换不把同管理根多环境、Arch/RPM 清单、通用单实例或私有 GUI 标成已验收。测试遵守 [全项目规范](测试禁令与规范.md)，现行宿主保留线 1 GiB，默认新增容器 0。
