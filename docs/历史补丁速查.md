# Unifier 历史补丁速查

在仓库根目录用 [repair_reference.py](../tools/repair_reference.py) 查询。脚本使用 Python 3.11+ 标准库，输出静态条目，不需要管理员权限，也不会读取用户状态、启动应用或修改实例。版本、症状、现行代码位置与历史证据都在条目里。

Beta 1 的桌面及安装回归已另附 [实测与补丁盘点](v0.0.8b1-桌面实测与补丁盘点-2026-11-19.md)，包含实际部署、原生正负向事务和仍待验收的应用路径。

```bash
python3 tools/repair_reference.py --list
python3 tools/repair_reference.py --release v0.0.7+wayland.2
python3 tools/repair_reference.py '输入法'
python3 tools/repair_reference.py 'guest prerequisite failed: ERROR application-python3-unavailable'
python3 tools/repair_reference.py --json 'ipc.node'
```

`--release` 按修复进入的版本筛选，可与关键词组合。`0.0.7.dev0` 和 `v0.0.7dev` 都查询正式版的同一补丁基线。多个关键词须同时匹配，英文大小写不限。`--list` 只列标题，`--json` 输出完整条目，无匹配时退出码为 1。证据路径相对于仓库根，`NextKde/` 开头的路径属于相邻的 NextKde 源码仓库。档案中的旧命令适用于原执行对象和版本。

## 按症状落到现行入口

先对照 `unifier --version`、实际启动器路径和 [当前状态](当前状态.md)。Beta 1 原包和客体运行时热修的版本字符串相同，以部署回执和文件清单核对实际构建。源码中的修复、日用安装与真实工作流回执各有适用范围。

| 症状 | 从哪里查起 |
| --- | --- |
| 包管理返回 `needs-recovery` | `unifier env inspect ENV`、`unifier pkg log ENV`、`unifier pkg show TXN`。按数据库和执行状态判断能否走正式 `unifier pkg recover ENV`。 |
| 有明确的 loader 缺库错误 | `unifier pkg repair-deps ENV --from-log ./runtime.log --diagnose-only` 只分类指定日志；有 ABI、符号、权限或未定位插件错误时看分类结果。 |
| 包已安装但菜单没有应用 | `unifier app show APP` 查启动登记。符合菜单导出条件且已有可用登记时用 `unifier app export APP --menu-only`。先查包验证状态、`NoDisplay`/`Hidden` 和 ELF 扫描阶段。 |
| XWayland 中文输入异常 | `unifier app input-method APP` 查登记偏好。明确使用 XWayland 且现有 X11 通道可用时，可选 `host-xim`。 |
| 又出现应用自己的 GTK 文件选择框 | 核对应用菜单的 `Exec` 所用版本、`unifier env portal-bridge ENV` 和 `unifier app file-chooser APP`。钉钉历史验证使用 `gtk-native-portal`。现有实例补桥接的流程见 [GTK 原生选择器兼容](GTK原生选择器兼容.md)。 |
| 文件选择后打不开，或者需要撤销 | 先看 `unifier app file-chooser APP`，再用 `unifier file access list` 查 lease/grant。对应授权可用 `unifier file access revoke LEASE GRANT` 撤销。 |
| QQ 菜单出现但进程未启动 | 如果报 `application-python3-unavailable`，查 Beta 1 运行时热修与对应客体包；包名模式的 `unifier pkg repair-deps ENV PACKAGE` 走正式事务补齐并核验。 |

命令中的 `ENV`、`APP`、`TXN`、`PACKAGE`、`LEASE`、`GRANT` 以对应管理根和当前登记为准。需要修改包、环境或执行实机回归时，按 [项目测试规范](测试禁令与规范.md) 和现行用例判断执行条件。

## 旧 Meeting 与新日用 Debian 的两处差异

**渲染设备。** 卸载前旧 Meeting 的环境登记和 Podman `Config.CreateCommand` 均显示原生 `/dev/dri/renderD128` 映射。新日用 Debian 原本未映射该设备，XWayland 仍可传入 DRI3 FD。客体 libdrm 枚举失败时，Debian Mesa 25.0.7 的 Iris 错误路径漏解锁，触发 GPU 看门狗。`0.0.8b1+render.1` 通过 `unifier env render-node ENV /dev/dri/renderDN` 为已停止且符合条件的实例配置一个节点，映射随 Unifier 启动生效。设备编号按实际 PCI/DRM 身份和权限核对。旧归档核对位置见 [迁移回执](../artifacts/v008beta-clean-install-20261117-MDi9pIbP/report.md)，诊断和原日用实例验证分别见 [GPU 对照实测](../artifacts/qq-standard-20261118-HlbtB4ve/report.md) 与 [日用验收](../artifacts/qq-render-node-daily-20261118-Vn2eRc48/report.md)。

**托盘和 Portal。** 旧 Meeting 按环境启用了 Portal 总线代理，新日用 Debian 当时未启用。两版 `xdg-dbus-proxy` 的 `org.kde.StatusNotifierWatcher` 放行规则相同。旧实例的注册方式缺少现场记录。新日用 QQ 通过 XEmbed 代理暴露 `ContextMenu`。KOS 为 `hasMenu == false` 的项转发点击。XEmbed 重放时必须使用 KWin 的实际指针位置，并按 XRandR 输出矩形换算到 XWayland 像素。屏幕中心和 X11 查询到的旧指针坐标都可能使重放失效。回归时从面板实点，核对每次动作的 D-Bus 实参、左键恢复窗口和右键弹出原生菜单。[KOS 实现](../../kde前端优化/NextKde/platform/src/daemon/PlatformServerTray.cpp) · [本轮验收](../artifacts/kos-tray-click-20261118-qcSxYAW7/report.md) · [原托盘调查](../artifacts/qq-system-diagnosis-20261118-7ONesT4M/report.md)
