## 资源边界

`tools/guarded_test.py` 是扩测工具，不改变日常产品运行方式。真实 fixture 只允许工作树 `.lab` 下的独立根和该 fixture 内的共享目录；禁止符号链接逃逸、宿主设备与桌面 socket。容器创建时固定 private IPC、core=0、768 MiB 内存、128 MiB swap、192 个任务、1 个 CPU，并进入测试汇总 slice。

```bash
systemctl --user start unifier-tests.slice
systemctl --user set-property --runtime unifier-tests.slice \
  MemoryHigh=768M MemoryMax=1024M MemorySwapMax=128M \
  TasksMax=256 CPUQuota=100% CPUWeight=10 IOWeight=10
```

测试控制器自身也必须在此 slice 中，且设置 `GOMAXPROCS=2`。仅给容器限额仍会留下宿主控制器消耗；过紧的控制器任务数限制又会使旧 Podman 的 Go 辅助进程创建线程失败。此次实机使用控制器 `TasksMax=96`，汇总上限仍为 256。启动控制器的形式为：

```bash
systemd-run --user --slice=unifier-tests.slice --setenv=GOMAXPROCS=2 \
  --property=MemoryMax=192M --property=MemorySwapMax=32M \
  --property=TasksMax=96 --property=RuntimeMaxSec=900 \
  --property=LimitCORE=0 /usr/bin/python3 /已核对的专用测试驱动.py
```

slice 属性是本次启动期的设置，重启后要重新建立和核对。控制器使用 `GuardedPodmanRuntime` 与 `HostReserveMonitor`，在 finally 中按完整 CID 收尾。不要把上述形式用于未经核对、可能操作日常环境的旧驱动。

每次创建/启动前至少保留宿主 2 GiB 加客体 768 MiB 的可用内存；不足则拒绝。运行中每秒检查，连续三次低于 2 GiB 时，只停止重新核对过的当前测试 CID。指标不可读也中止测试。若实例身份核验失败，不发送停止命令，留下 `stop_error` 供复核。中止还会在 fixture 的宿主父目录写入 `.guard-abort.json`，新的保护运行时实例也会拒绝启动；只能在复核精确 CID 已停止、资源门槛满足并保留回执后，明确开启新一轮。任何中止都不能记为应用正常退出、包事务成功或长压通过。

core=0 限制转储，不承诺所有异常退出都不会触发宿主崩溃通知。应先限制 Go 并发、任务数和总内存，并避免让应用在用户桌面反复崩溃。资源不足时继续离线或远端有界测试，不降低宿主预留线。

应用启动必须沿用同一个保护适配器，包括新的 CLI 工作进程。只在外层控制器做预检、再调用使用普通运行时的独立应用工作进程，会留下自动重启绕过软门槛的机会。当前私有驱动通过受控入口为实际 app CLI 注入 `GuardedPodmanRuntime`；前置操作失败立即放弃后续命令。原日常 CLI 的行为没有因此改变。

## 中断后恢复

先核对容器完整 CID、环境 UUID/generation、runtime 所有权标签、宿主启动身份和会话 PID/start。不要为探测旧状态而启动旧图形容器，不删除租约文件来跳过未知状态。

项目会话恢复可从精确相同且已停止的容器证明原客体执行结束；替换 CID、代际变化、外来标签或无法 inspect 都保持未知。包事务按 `pkg recover` 重新核验原生数据库和包清单，不自动重跑先前的安装脚本。独立数据库可只读执行完整性检查；中断前保存的数据不能替代完整 30 分钟稳定性验收。
