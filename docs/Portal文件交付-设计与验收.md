# Portal 文件交付：设计、验收与剩余问题

2026-11-11。钉钉本次人工上传已通过，日常 r6 已部署。本提交保存这条功能链及必要前置模块；不是对全部桌面集成、所有应用或共享文件系统的验收。启用方法、平台条件和限额见 [GTK 原生选择器兼容](GTK原生选择器兼容.md)，可移植的脱敏回执见 [验收记录](../artifacts/portal-file-delivery-20261111/README.md)。

后续工作树更新：PD-01～03 的首批行为修复已实现，见 [第一批修复验收](Portal首批修复验收-20261111.md)。下文缺陷表保留 r6 / `f35ffe99` 的审查基线；新修复尚未部署，不改写既有人工上传记录。

## 本轮查明的两处断点

1. **选择器入口与探测对象不一致。** 钉钉上传使用自己的 GTK 路径，CEF 的 Portal 探测成功不代表该路径采用 Portal。其 GTK Native 动态加载尝试无版本名 `libgtk-3.so`，客体只有运行时库 `libgtk-3.so.0`，导致 Native 分支不可用。`gtk-native-portal` 在客体私有目录建立经过 ELF、SONAME 和符号归属核验的别名，只影响该应用的加载环境。没有按钉钉版本打二进制补丁。
2. **窗口转发与文件可达性脱节。** r5 已实际到达宿主 KDE Portal，但宿主选中的非共享文档在客体同路径不存在。既有 `file_routes.py`/kdialog 路径转换没有接入原生 GTK 返回；工作树中已有宿主路径策略和 openat2 检查，也不等于已经接入发布版。r6 补上成功选择后的授权和交付。

这两处是串联故障：只修第一处能出现正确选择框，仍无法上传。验收必须覆盖消费者实际读取，不能停在环境变量、Portal 版本探测或窗口外观。

## 当前交付契约

```text
应用 → files-bus → 既有 xdg-dbus-proxy → 宿主 Portal
应用 ← 客体可达 URI ← 对应成功 Response / 宿主 owner 核验
                        ├─ 已共享：核验实际挂载后转换路径
                        └─ 未共享普通文件：固定源描述符 → 有界快照 → 既有桥接挂载
```

- `gtk-portal`、`gtk-native-portal`、`qt-portal` 共用交付通道；kdialog/zenity 仍走原有命令适配器与静态共享。统一后者的交付语义尚未完成。
- 每个连接独立上游唯一名，关联方法序号、请求路径和宿主 Portal owner。只有相应成功结果才能交付；取消、Close、错误及已记录的重复响应不复制文件。
- 共享路径以运行时真实 bind 为准；源描述符复用 `host_share_policy` 与 `host_share_paths`。上传副本保存原文件名、字节内容和初始只读权限，宿主原件不被写入。
- 未共享的目录、可写选择、SaveFile/SaveFiles 明确失败；此实现不是原件编辑、双向同步或 Documents Portal 的完整替代品。静态可写共享继续承担保存语义。
- 宿主须有 `/usr/bin/python3` 的 GIO 绑定和 xdg-dbus-proxy；当前 Native 库适配限定 GTK3/amd64。其他架构未通过验收，不能从 openat2 helper 支持 aarch64 推定 Native 启动器也支持。
- 最终环境应用租约结束时清理快照；正常运行中保留已交付文件，避免异步上传读取时提前删除。限额见使用文档。

入口、CLI、实际挂载解析及 GTK Native 前置功能此前也未提交，所以本次必须一并保存；否则仅提交 r6 的两个新模块会留下缺失导入和不可达入口。FUSE 视图、Dolphin 动态授权、资源树和其他脏改动不在提交内。

## 授权边界必须说清楚

当前信任边界是**同一个 Unifier 环境及宿主 UID**。桥接目录由同一环境的应用共享，认证检查同 UID；不是应用级文件隔离，也不把 0400 权限当作同 UID 下不可修改的安全边界。`host_share_policy` 在本入口以用户已选文件的父目录构造一次性路径检查，不代表其他入口配置的黑名单或管理员目录规则已全局接入。

“用户选择了一个文件”“允许哪个应用访问”“实际以什么 URI/FD 交付”“什么时候撤销”需要成为同一资源授权对象的字段。现有实现补通只读上传链路，但尚未统一静态 FileRef、Portal、命令助手和将来的动态共享视图。后续不能仅凭宿主路径字符串在各入口分别判断。

## 尚欠缺的设计及具体问题

下列是现行源码可见的限制或控制流问题。除已记录的钉钉失败外，不声称已经在用户桌面复现异常；本次提交不混入新的行为修补。

| --- | --- | --- | --- |
| PD-01 / 优先 | `Client.expire()` 在 300 秒后仅取消并遗忘请求，未向应用发送终态；晚到 Response 又被 retired 路径规则丢弃。长时间停留在选择框后可能无法完成。 | 请求状态机统一 timeout/Close/disconnect/late Response；保证终态恰好一次，并关闭相应宿主请求。 | 私有总线虚拟时间测试：超时、晚到成功、取消竞态均终止等待且无授权残留。 |
| PD-02 / 优先 | `start_bridge()` 遇到存活 bus 配合已死 delivery 时，只 `_terminate` 旧 delivery 再覆盖记录；未复用 `stop_bridge()` 的目录身份清理。异常重建可能留下旧快照。 | 持久化快照归属/代际与恢复状态；重建前按身份回收旧记录，清理幂等，失败保留诊断。 | 私有 fixture 注入 relay 崩溃和重建，旧目录回收、活动文件不误删、失败可恢复。 |

- r5 实时观察确认了 GTK Native → public Portal → KDE 后端 → 取消响应，随后上传失败被保留为失败，不改写为通过。
- r6 产品持久审计记录成功选择、930304 字节快照、客体 URI 交付、IN_ACCESS；用户明确确认上传成功。该次发生在被动观察器退出之后，没有完整 KDE 后端实时轨迹或服务端上传回执。读取事件不独立标识具体读取进程，上传完成依据用户确认。
- 原工作树 919 项离线测试（5 跳过），日常候选 66 项（0 跳过）通过。该结果不等于本次独立提交快照；后者单独运行，915 项（5 跳过）、语法/别名/CLI 检查通过。
- 尚缺真实 Qt、其他桌面/架构、目录和原件写回、多应用隔离、FD 传递专门用例、长驻配额及上述异常恢复验收。一次钉钉成功不外推为所有应用兼容；人工观察不等于 PRE03/T3 自动化准入。

验证装置也需要分层预算：本次暂存检查暴露了将约 257 MB Git 历史快照导出到内存盘的开销。大源码/历史证据快照应使用可回收的磁盘临时存储；短 socket/TMPDIR 仍由统一保护器管理。保护中止、fixture 故障和产品故障必须保持不同状态，不靠调低阈值换取绿灯。
